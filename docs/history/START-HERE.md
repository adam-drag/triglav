# Planning prompt: AI consultancy orchestrator

Copy the prompt below into a new LLM conversation and attach `PROJECT-BRIEF.md` and `ROLES-AND-WORKFLOWS.md` from this folder. If the LLM can read local files, give it this folder and ask it to read all three files. The two supporting files contain the project context and proposed workflows.

---

You are the founding technical lead planning a greenfield product: a dashboard and coordination service for AI agents that work like a software consultancy, with me (a human) as the Client. Client is not an assignable AI agent role.

Read the attached `PROJECT-BRIEF.md` and `ROLES-AND-WORKFLOWS.md` before planning. Treat explicitly stated requirements as requirements. Treat proposed defaults and candidate features as options to evaluate. Do not silently turn suggestions into commitments.

Your task is to produce an actionable product and technical plan. Do not write application code, scaffold a repository, provision infrastructure, or begin implementation. Architecture diagrams, interface descriptions, state tables, and planning Markdown are welcome. Do not create real Linear tickets or change external systems during planning.

## How to work with me

- Act like a Staff Software Engineer who owns delivery. Make routine, reversible product and engineering decisions and explain the important ones briefly. Do not send every decision back to me.
- Ask only questions whose answers materially change the product, feasibility, security boundary, operating cost, or implementation scope. Group essential questions into one short batch. Continue planning the independent parts while answers are pending. `PROJECT-BRIEF.md` lists inputs I have not stated yet. Check that list first.
- The message board has the most detailed requirements in this pack. That does not make it the highest-risk area. Rank risks from your feasibility findings.
- When an answer is unavailable, distinguish an explicit assumption from a verified fact. Mark consequential unresolved decisions clearly. Never invent APIs, commands, SDK features, provider permissions, or background execution capabilities.
- Research current official documentation for Codex, Claude, Linear MCP, and any proposed integration mechanism before relying on their capabilities. Distinguish desktop apps, CLIs, SDKs, APIs, and hosted services. Name the exact product surface being evaluated. If research is unavailable, produce a provisional plan and identify the capabilities that must be verified.
- Prefer the smallest coherent vertical slice that demonstrates the consultancy workflow. Avoid speculative infrastructure and premature generalization.
- Write plain, professional English. Use no em dashes.
- Open the plan with three short parts before section 1: a TL;DR of one or two lines, an executive summary of a few lines with the key decisions and tradeoffs, and a bullet list of notable specifics and open risks. Each part must make sense on its own.

## Required message board workflow

A Senior posts a question with the internal job ID, owning Staff agent ID, job-description reference, Linear ticket link, enough inline context for unfamiliar helpers, and a response deadline. Use a five-minute response window as the initial default, configurable to a shorter duration when posting. The owning Staff agent monitors its jobs by polling, long polling, or SSE and answers in the thread. Researchers monitor all board messages across all accessible jobs and can join any discussion without an assignment or invitation.

The Senior waits the full declared window, even after an early Staff answer, and then considers every answer received by the deadline before acting. It does not wait for every registered researcher. Staff retains decision authority. Define how conflicting advice is synthesized, missing required Staff decisions keep dependent work waiting, and late replies are handled. Do not replace this workflow with first-answer-wins behavior or invitation-only specialist participation. Follow the detailed message board requirements and acceptance example in `ROLES-AND-WORKFLOWS.md`. The board is inspired by the message board that agents built for themselves in the 2026 OpenAI and Hugging Face incident. Read the sources linked in `ROLES-AND-WORKFLOWS.md` and apply the lessons listed there.

All board messages must be persisted and readable in the human Client's dashboard. The Client can post and reply on the board. Researchers can discover human messages through the same all-jobs feed and support, approve, challenge, disagree with, or reject proposals with reasons. Persist and display the full discussion and distinguish each participant's assessment from the final authorized decision. Include this human participation flow in the v1 UI and acceptance demonstration.

## Questions the plan must resolve

1. What runs an agent? Separate the model, execution runtime, role, agent identity, session, and assigned job. Explain which component starts, supervises, pauses, resumes, and terminates work. A database record alone does not create a running worker. Start from my intended model in `PROJECT-BRIEF.md` under "Intended operating model".
2. What does initial support for Codex and Claude mean in concrete terms? The orchestrator never starts agents. A session I start registers itself, and it starts other agents with the tools of its own CLI. For each CLI, verify how a session can start other agents, whether those agents can reach the orchestrator, how long they can live, whether they can wait for events, and what happens to them when the parent session ends. If spawned agents share the parent's connection to the orchestrator, the orchestrator cannot tell them apart by connection, so define how every call identifies and authenticates its agent. Do not presume that a chat can remain alive indefinitely, listen for events, or spawn another provider's agent.
3. How can an agent join through a common protocol, receive a role contract, discover authorized work, report progress, exchange messages, and leave? Evaluate MCP for agent-facing operations, and SSE versus long polling for event delivery. Explain how execution resumes when the chosen client cannot listen continuously. A session that I tell to wait for questions must be able to wait for a long time without my input. For each CLI, verify how it can wait (for example a blocking tool call, a background command, or a hook) and what limits apply, such as tool call timeouts, permission prompts that stop an unattended session, and context growth after many wake-ups.
4. How do Linear tickets and subtickets map to internal job requests? Specify which system owns each field and status, what synchronizes in v1, and what happens when they disagree. Linear is the initial task source; internal orchestration state is stored in MySQL.
5. How do Staff, Senior, Reviewer, Researcher, and Specialist responsibilities interact? Roles and skills must remain independent of model names. Show how multiple agents can contribute without competing for ownership or generating endless discussion.
6. How do we distinguish a healthy agent waiting for work from an expired session, a disconnected agent, and an abandoned job? Define presence, heartbeats, leases, reconnect behavior, and recovery. An expired agent should disappear from the active roster while its historical identity and contributions remain visible.
7. How does the client see real progress, decisions, review evidence, blocked work, and the next action needed? Propose a minimal dashboard before expanding it.

## Required planning output

Produce these sections in this order:

1. **Product definition and scope:** a concise interpretation of the idea, actors, the core user journey, hard requirements, assumptions, v1 inclusions, and explicit exclusions.
2. **Feasibility matrix:** for Codex, Claude, Linear MCP, and the proposed orchestrator protocol, record the required capability, verified support, integration surface, documentation source, limitations, and fallback. Separate confirmed capabilities from open questions.
3. **Recommended architecture:** explain component responsibilities and deployment boundaries, with a small diagram. Show the Docker Compose services and how agent sessions running on my machine reach them. Compare only meaningful alternatives. Recommend a stack with reasons, preserving MySQL unless you explicitly propose and justify a deviation for my decision.
4. **Domain and lifecycle design:** define the main entities, relationships, job states, allowed transitions, transition authority, review outcomes, client escalation, and completion criteria. Include ownership and concurrency rules. Use conceptual tables rather than executable schemas.
5. **Agent contracts and coordination:** define role instructions and reusable skill responsibilities; registration and session lifecycle; logical tool/API operations; event delivery; message threads; correlation identifiers; reconnect and duplicate handling; owner-scoped and all-jobs subscriptions; durable response deadlines; full-window waiting and collection of all timely answers; and bounded discussion loops with open researcher participation. Outline the orchestrator usage guide that every session reads, and give the short start prompt I type for each role I start by hand (Staff and researcher). Define the registration pattern that Staff passes to the Seniors it starts. Decide whether agents learn the orchestrator from a Markdown guide that it serves, from its MCP server, or from both. Proposed interface names are design proposals, not existing APIs.
6. **One end-to-end walkthrough:** follow a Linear parent ticket and two subtickets through Staff registering the job, Staff planning, Staff starting Seniors that register themselves, Senior assignment, a design question, a specialist answer, implementation evidence, review feedback, revisions, and completion. Include an early Staff reply and later researcher contributions within a five-minute response window, demonstrating that the Senior waits the full window. Include one genuine client blocker and one agent failure, showing recovery for each.
7. **V1 dashboard:** describe the minimum screens, fields, filters, and client actions. Start with job list, job detail with discussion and review, active agents, and a visible queue of client decisions. Label additions beyond v1.
8. **Operational boundaries:** cover scoped credentials and permissions, untrusted ticket/message content, workspace isolation, approval boundaries, cancellation, retry limits, timeouts, cost/concurrency controls, audit history, and recovery. Be proportionate to a first version for one client.
9. **Delivery plan:** propose small milestones and an ordered backlog with dependencies, acceptance criteria, and how each milestone will be demonstrated. The first milestone should prove the highest-risk integration assumption. Include a later two-provider end-to-end demo. Include a way to test the coordination rules, such as response windows, leases, and stale results, with scripted agents and a controllable clock instead of paid model calls. Do not give precise estimates without a stated basis.
10. **Decision log and open questions:** distinguish decisions made, assumptions, verified facts, unresolved feasibility checks, and decisions genuinely requiring me. End with the concrete next planning step, not application code.

For each major design choice, state the problem it solves and its simplest adequate implementation. Explicitly check these failure cases: duplicate assignment, stale worker submitting results, lost events, duplicate messages, agent death while holding work, Staff unavailability, conflicting reviews, dependency failure, Linear downtime, and a review loop that never converges.

The plan is complete when an engineer can identify what to build first, how agents coordinate, how completion is proven, and how the system recovers when an agent disappears. It must also clearly identify any unverified capability that could invalidate the recommended architecture.
