# Working on Triglav (for AI coding agents)

This file is for an AI agent that changes this repository. The agents that Triglav itself coordinates (Staff, Seniors, reviewers, researchers) do not read it: their instructions are the role cards in `src/guide/`. README.md covers setup and use; read it first.

## What it is

Triglav is a local orchestrator for AI agents working on Linear tickets like a small consultancy. A Staff agent (Claude Code) plans and delegates, Seniors (Claude Code subagents of Staff) implement, researchers (short Codex runs) advise on a message board, and the Client (a human) decides from a React dashboard. Everything an agent does goes through MCP tools in `src/mcp.ts`, so the Client can see it.

Two processes:

- **The server** runs in Docker (`docker compose up -d --build`): Fastify, MCP endpoint at `/mcp`, dashboard API, SSE, a scheduler tick, MySQL 8.4. It cannot start processes on the host.
- **The host runner** (`scripts/runner.ts`) polls `/api/runner/next` and starts what the server queued: Staff resumes, researcher runs (`codex exec`, or `claude -p` when the runner found no Codex). It also reports which agent CLIs are installed (`scripts/runtimes.ts`, `/api/runner/runtimes`). It builds every command itself and validates every field. Never make it run a command string from the server.

## Invariants

- **The orchestrator never decides for the Client.** Merges, deploys, force pushes and repository settings are the Client's. Client decisions are blockers the Client resolves in the dashboard.
- **The Operator asks, the Client decides.** Its `claude` process is read-only: `--permission-mode dontAsk`, `--tools Read,Grep,Glob` and a fixed allow-list (`OPERATOR_TOOLS` in `scripts/operator.ts`). It has no Bash: a read-only-looking prefix such as `git log:*` still lets `--output=FILE` write. A host command it needs is a tool in `scripts/operator-host-tools.ts` with a fixed argv and a strict schema; never add a Bash rule or a tool that takes options or a command string. Its only Triglav MCP server is `/operator/mcp`, scoped by a per-chat token (`src/operator.ts`); never expose it through `/mcp`, which agents can reach. The token is minted when the runner starts a process for the chat (`issueChatToken` in `src/chat.ts`), only its SHA-256 is stored, and it reaches `claude` in a 0600 file (`scripts/private-file.ts`), never in argv. When the process ends the runner revokes the token (`revokeChatToken`, which clears the hash only if it is still that token's). On SIGTERM, SIGINT or SIGHUP the runner first stops the Operator processes and waits (up to 3 s) for those revocations (`OperatorChats.shutdown`); a runner that is killed hard leaves its tokens, and `resetChatStates` clears them when the next runner says hello. Its other MCP server is the local stdio `host` server (`scripts/operator-host-mcp.ts`) with the fixed host tools. A change goes through a `propose_*` tool, which only records a pending request (`src/operator-actions.ts`). The card text is written from the database, never from the model's words, the action is validated again when it runs, and nothing runs until the Client clicks Confirm. Add an action to `ACTIONS` with a `describe` that reads the database; one that must run on the machine becomes a `host` command that `scripts/operator.ts` runs from a fixed list.
- **Three credentials, three audiences.** `ORCH_ENROLLMENT_KEY` is held by agents and opens `/mcp` only. The host runner also reads it from `.env`, for one purpose: the MCP config file of a Claude research run (mode 0600, written per run, removed when the run exits). It never reaches a child's environment, arguments or a log (`staffStartEnv` drops it), and `scripts/runner.ts` never uses it to call the runner API. `ORCH_RUNNER_KEY` is held by the host runner and opens `/api/runner/*` only; the server refuses to start if it is missing, shorter than 24 characters or equal to the enrollment key. The Client's session cookie (password set with `scripts/set-password.ts`, only a scrypt hash in `ORCH_CLIENT_PASSWORD_HASH`) opens every other `/api/` route. The guard in `src/server.ts` matches the route pattern and denies by default: every `/api/` route needs the Client session by default; add a route to `OPEN_API_ROUTES` only when it must work without a session, which is rare. Agents run as the same OS user, so this raises the bar and is not a hard boundary; say so when you document it.
- **The public dashboard listener serves the dashboard and nothing else.** It is opt-in: `buildServer` gets `dashboard` only when `ORCH_DASHBOARD_URL` is set (`readListenerConfig` in `src/config.ts`), and `src/main.ts` then starts a second app on `ORCH_DASHBOARD_PORT` (7410). Without it nothing changes on port 7400. On the public app an `onRequest` hook checks the Host (equal to the URL's host), the Origin on every non-GET (equal to the URL's origin) and the route pattern (`publicRouteAllowed` in `src/server.ts`, deny by default) before the static `/*` fallback, so `/mcp`, `/operator/mcp`, `/api/runner/*`, the stop hook, the status line usage and `/guide.md` are 404 there whatever credential is sent. A new Client `/api/` route is reachable there with a public session; a new open route or a new non-API route is not, unless you add it to `PUBLIC_OPEN_ROUTES` or the allow-list, which needs a reason. Sessions carry a scope (`client_sessions.scope`, `local` or `public`) and each listener accepts only its own; public sessions last 7 days in a `__Host-` cookie. The public login has its own limiter (`PublicLoginLimiter`: per client address and a total cap), a 16-character minimum, and a login record (`client_logins`). The client address is the rightmost `X-Forwarded-For` entry when it is an IP, read only on the public listener; never enable Fastify `trustProxy` (it rewrites `req.host` and `req.protocol` from `X-Forwarded-*`), and never build a rule on the source address (a request from the host through Docker's published port arrives as 172.17.0.1). `ORCH_PUBLIC_URL` stays a loopback URL: it is the agents' and the runner's base URL, never the dashboard's. A remote Client session has full control of the host, so this raises the bar and is not a hard boundary; say so when you document it.
- **Nothing started by the runner gets the orchestrator's secrets.** Every process the runner starts (resumes, research runs, the Operator, its host commands) gets `staffStartEnv(process.env)`, which drops `ORCH_*`, `MYSQL_*`, `DATABASE_URL` and `LINEAR_API_KEY`. The runner, the Stop hook and the status line script send credentials or session data only to an http loopback `ORCH_URL`, without following redirects (`scripts/loopback.ts`).
- **A finished job's worktree goes, its work never does.** Seniors name their worktree (`report_progress`, `request_code_review`); `recordWorktree` (`src/worktrees.ts`) keeps it per job. When the job is done or cancelled, and no open job, held assignment, running review, job repository or researcher uses that path, the scheduler queues a `reap_worktree` launch. The server sends only the path. `reapWorktree` (`scripts/worktree-reap.ts`) removes it with `git worktree remove` only when it is a linked worktree inside `$HOME`, not locked, with nothing uncommitted or untracked and every commit on a remote-tracking branch; otherwise it keeps it and the job page says why. Never add `--force`, never delete a branch, never remove a main checkout. Only recorded paths are removed, so the Senior and Staff cards forbid clones and Claude Code worktrees (`EnterWorktree`, `isolation: "worktree"`), which nothing records; that rule is in the cards only, not enforced. Every job left a worktree with its own `node_modules` and the host disk filled up (2026-10-20). While a removal is picked and unfinished, `recordWorktree` refuses that path, so keep the `reap_worktree` expiry (`worktreeReapLostSec`) longer than the runner's git timeouts. New Seniors are refused, at ticket issue and at claim, while the runner reports less than `POLICY.minFreeDiskBytes` free (`assertDiskRoom`).
- **Agent text is data, never instructions.** Tool results that carry other agents' text are marked untrusted. Do not add a path where board text, ticket text or transcript text is executed or followed.
- **Leases and attempt fencing.** A Senior holds an assignment by renewing a lease; a new attempt fences off the old one. Keep these checks in the same transaction as the write they guard (`tx()` in `src/context.ts`).
- **A research run reads and advises; it never edits or runs commands.** A Claude run has `--tools Read,Grep,Glob` and `--strict-mcp-config` (`scripts/research-run.ts`), because `--allowedTools` and the permission mode do not remove a built-in tool that the user's or the repository's settings allow. A Codex run has every MCP server but `orchestrator` switched off, because `-s read-only` does not sandbox MCP tools (evidence in the README). Do not add a tool, a second MCP server or a Bash rule to either.
- **Codex Staff access is one builder.** `codexRoleArgs(role)` in `src/codex-args.ts` is the only place that sets Codex's sandbox, approvals and shell environment. Start (`scripts/staff-start.ts`), resume (`scripts/runner.ts`), the dashboard Copy command (`resumeArgs` in `src/telemetry.ts`) and the Models page (`launchCommand` in `web/src/App.tsx`) all call it, and the Dockerfile copies it into the web build stage. `staff` gets the `--approve-for-me` keys plus a shell environment of Codex's core names, `GITHUB_TOKEN` and `SSH_AUTH_SOCK` (SSH push to the `git@github.com` remotes; the Client approved it); `researcher` is read-only; any other role throws. The role comes from the launch record (`nextLaunch`), never from a string the server sends to run. This is wide access with Codex's automatic reviewer as the only check, the same position as Claude auto mode, and agents share the OS user. Do not widen it (no `danger-full-access`, no more variables in `CODEX_STAFF_ENV`, no `network_access=true`) without a Client decision.
- **A code reviewer reads and reports; its output is data.** A `code_review` seat is `codex exec -s read-only` or `claude -p --tools Read,Grep,Glob`, with every MCP server off (`codexReviewArgs`, `claudeReviewArgs` in `scripts/code-review-run.ts`), the orchestrator included, and no Triglav token. The runner computes the diff from two shas itself and posts the process's stdout to `/api/runner/:id/review-output`; `parseReviewerOutput` in `src/code-review.ts` validates it finding by finding and caps it. A failed, cut or unparseable seat makes the review `failed`, which never counts as a pass. The one exception is a shadow seat (a lens seat with `shadow` on, the default for the contracts and integrity lenses): its findings are stored and shown but never block (`blocks()` ignores a finding that only shadow seats reported), it is not in the round 2+ list to answer, and its failure does not fail the review; a review where no blocking seat finished fails. Shadow seats can never make a review pass, and a lens seat gets the same read-only command as every other seat. `code_review.finished` goes to the requesting Senior only and is not a Staff wake type. Do not add a tool, a Bash rule or an MCP server to a reviewer. Which seats run, and on which runtime, model and effort, is the Client's setting (`settings` row `review_panel`, edited on the Models page, read by `requestCodeReview` when a review is requested, `DEFAULT_PANEL` when there is none). A Senior, Staff or an agent never chooses or changes the panel, and its routes (`/api/review-panel`) are Client-session routes, never in `OPEN_API_ROUTES`. The job page shows reviewer text as plain text only: no markdown, no links, no `dangerouslySetInnerHTML`. The instructions are `buildReviewPrompt` in `src/code-review.ts`: Copilot's workflow as numbered steps (questions, a mandatory search of the repository, the repository rules, the ticket and PR claims, edge cases, tests, verify and group by pattern), with the ticket, criteria and PR notes marked as data. A test (`test/code-review.test.ts`) checks that each step is present. The server prompt must stay under `MAX_SERVER_PROMPT_CHARS` (100000, the runner refuses more) and the previous-findings list under its own 60000-character budget.
- **The local review gate is server-side; the Copilot gate is a bar.** `submit_review_package` needs `head_sha` and is refused unless a finished local review of exactly that sha has the verdict `ok` (`gateAt` in `src/review-gate.ts`), in every review mode. A piece of work is the commits since the last passing gate: at most 3 local rounds (more only when Staff resolves the failed_execution blocker the Senior raised at the limit), round 2 and later must use the previous reviewed head as `base_sha`, and a failed review is not a round. The reviewed ranges of a job are one chain: round 1 of a piece must start at the job's last passing head, or else at the merge base of the head with `origin/<job base_branch>`. The server cannot run git, so `requestCodeReview` marks the case (`code_reviews.expect_merge_base` and `base_branch`, or `expect_ancestor` for a piece that starts at the last passing head, all on the launch) and `worktreeDiff` in `scripts/code-review-run.ts` verifies it (`checkMergeBase`, `checkAncestor`; the runner never fetches, a missing `origin/<branch>`, a different base or a head that does not descend from the last passing head fails the seat). `BASE_BRANCH` exists in both `src/code-review.ts` and `scripts/code-review-run.ts`; change both. Copilot rounds are asked with `request_copilot_review` and recorded with `record_copilot_result`: at most 3 per PR, none after "Approval recommended" or a round with no P0-P2 finding that was not "Previously missed". The server cannot run `gh` and Seniors still have it, so the Copilot gate raises the bar and is not a hard boundary, and the counts are the Senior's own report. Say so when you document it. The 3 and 3 in `src/review-gate.ts`, `src/guide/deliver.md` and `src/guide/senior.md` change together (a test checks the card).
- **The PR comment of the local reviews is built from the database and posted by the Senior.** `get_review_comment` (`src/review-comment.ts`) returns the text for a job and a head sha, for a Senior with a live assignment on the job or its Staff, and only when `gateAt` passes. The first line is the marker `<!-- triglav-local-review job=<job id> -->`; the card (`src/guide/deliver.md`) has the Senior post it once with `gh pr comment` and edit that comment by marker later, never a second one. Every untrusted string (titles, reasons, failure text, sites, model names) goes through `codeSpan`, so a mention, link, HTML or markdown in it cannot render; do not put any such text outside a span, do not add the finding body or a link outside GitHub, and keep the body under `MAX_COMMENT_CHARS`. `assertNoSecrets` runs on the body. The server cannot run `gh`, so this is a bar, not a hard boundary. Say so when you document it.
- **Researchers never wait.** They have no session between runs. Routing into the inbox happens in `emit()` (`src/events.ts`), the dispatcher in the scheduler tick (`src/research.ts`). A run trades a one-off ticket for a session token, marks every item, and exits.
- **Token cost is a design constraint.** Every return of a wait is a model turn that re-reads the agent's whole context (300k to 700k tokens for a Staff). That is why Staff wakes only for `STAFF_WAKE_TYPES`, Staff waits 3000 s on its one-hour prompt cache, Seniors wait 240 s on their five-minute cache, Staff compacts at about 280k tokens, and researchers run on demand. Measure before and after a change that affects turns or context size (transcripts under `~/.claude/projects` and `~/.codex/sessions`; Claude Code writes one line per content block with repeated usage, so dedupe by `message.id`).
- **Agent-facing text is terse; Client-facing text is plain full sentences.** The guide's "Write for the reader" rule applies to anything you add to prompts or tool descriptions.

## Where things live

See the Layout table in README.md. A few cross-file couplings:

- `STAFF_CLAUDE_SETTINGS` (`{"autoCompactWindow":300000}`) exists in three copies: `src/telemetry.ts`, `scripts/runner.ts`, `web/src/App.tsx`. Change all three.
- The guide is assembled per role in `loadGuide()` (`src/mcp.ts`) from `src/guide/*.md`. A new card or role must be added to `CARDS` there.
- A new launch kind needs: an insert into `launches` (with `kind`, `run_id`, `ticket`), a branch in `nextLaunch()` (`src/telemetry.ts`), a branch in the runner, and handling in `/api/runner/:id/exited` (`src/server.ts`).
- Two guides, kept apart. `src/guide/*.md` is for agents: served at `/guide.md` and by `get_guide`, never shown in the dashboard. `web/src/user-guide.md` is for the Client: bundled into the dashboard and shown on the Guide page. When a page or flow changes, check the user guide.
- Presence is derived, not stored: `presenceOf()` in `src/agents.ts` from `last_seen_at`, `waiting_until` and `transcript_at`. Researcher personas override it in `listAgents()`.

## Project skills

`.claude/skills/` holds short maps of the main areas, so you do not have to scan the repository to learn how an area works. Claude Code loads one when its description matches the task: `triglav-agent-sessions` (registration, presence, events, waits), `triglav-jobs-and-leases` (job lifecycle, leases, review, delivery, blockers, board), `triglav-runner-launches` (launches and the host runner), `triglav-operator`, `triglav-research`, `triglav-models-and-usage`, `triglav-server-and-auth` (routes, credentials, MCP tools, guide cards, migrations), `triglav-code-review` (the local review panel), `triglav-dashboard`.

- Use the matching skill before you read the code, and treat it as a map, not as proof. If a skill and the code disagree, the code is right.
- **When you find a skill out of date, update it.** Fix it in the PR you are working on; do not open a separate one. A change that moves a file, renames a function, changes a flow or adds a route, tool, launch kind or event type also updates the skill that describes it.
- Keep skills short and about how things work, not a copy of the code. Put only facts you verified in them, and update the "Verified" date line when you re-check one.

## Change, test, deploy

- Node 24 runs TypeScript directly (type stripping). No server build step. `pnpm typecheck` checks server and web.
- Schema changes: add the next numbered file in `src/migrations/` (applied in name order at start, one statement at a time). Never edit an applied migration.
- The e2e stack has its own test-only keys and password hash in `docker-compose.e2e.yml`; the fixtures log in with the password in `e2e/sim.ts` (`PASSWORD`). Call the Client API from a test with `clientFetch`, the runner API with `RUNNER_KEY`.
- Unit and coordination tests need the throwaway MySQL: `docker compose -f docker-compose.test.yml up -d --wait`, then `ORCH_TEST_DATABASE_URL=mysql://root:test@127.0.0.1:33061/mysql pnpm test`. Always cap vitest workers (`pnpm test` already passes `--maxWorkers=4`); the default froze this machine once.
- Browser tests: `pnpm e2e:up`, `pnpm e2e`, `pnpm e2e:down`. The e2e stack on :7401 runs the image built at `e2e:up`, so rebuild it after changing code.
- Deploy: `docker compose up -d --build`. It restarts the server, which cuts every open agent wait (agents retry) and any long-running probe against :7400. Use the :7401 stack for experiments that must survive a deploy.
- After changing `scripts/runner.ts`, restart the runner: `pkill -f "^node scripts/runner.ts$"`, then start it again with `nohup node scripts/runner.ts >> ~/.local/state/triglav/runner.log 2>&1 &`. Use the anchored pattern: an unanchored `pkill -f` also matches and kills your own shell.
- Telemetry skips transcript files whose size and mtime did not change (`telemetry_files`). To force a re-read, delete the file's row.

## Facts verified the hard way

- Which CLI a role uses: `effective()` in `src/models.ts` swaps a saved runtime that the runner reported missing for the only one it found, with `FALLBACK` models, and never writes it to `role_models`. Read role models through `effectiveRoleModel`, not by SQL. The runner also reports each CLI's own model list (`codex debug models`; Claude Code's stream-json `initialize` reply), and `updateRoleModel` refuses a model or effort outside it. Dropdowns in the dashboard come from that list (`ModelPicker`); with no list they fall back to text fields. A report older than 15 minutes counts as unknown, and unknown changes nothing. Resumes of existing sessions use the session's own runtime.
- Review mode (`settings.review_mode`: auto, copilot, ci_only) is the Client's choice. `reportDelivery` refuses `SKIPPED` when it is `copilot`; a Senior never decides to skip a required review. The map's "waiting on Copilot" dot comes from `copilotLoop` in `src/telemetry.ts`, which matches the `gh` commands of `src/guide/deliver.md`: change them together (`test/telemetry.test.ts` reads the card and checks both commands).
- A long poll must stop when its client hangs up (`nextCommand` in `src/chat.ts`): a restarted runner would otherwise lose the message the dead poll took.
- `claude -p --bare` fails with "Not logged in" (it skips the OAuth login), so the Operator does not use it. `--permission-mode dontAsk` with `--allowedTools` runs an allowed command and denies every other tool, verified 2026-10-11. In `--output-format stream-json` a `rate_limit_event` carries `unifiedWindows.five_hour.utilization` and `seven_day`; the scale (a fraction) is an assumption, see `translate()` in `scripts/operator.ts`.
- Claude Code honors an MCP `timeout` of 3500000 ms; a 3000 s tool call returned cleanly (2026-10-09). The Codex `tool_timeout_sec` is 330.
- `claude --settings '{"autoCompactWindow":300000}'` gives `effectiveWindow=280000` (debug log). The default for Opus is 980000, so Staff never compacted.
- Staff writes its prompt cache at the one-hour TTL; subagents (Seniors) at five minutes.
- The runner starts `claude -p` research runs with `ENABLE_CLAUDEAI_MCP_SERVERS=false`. On an account that has a claude.ai connector, Claude Code can drop a local MCP server of the same name in favour of the connector, and a connector cannot do OAuth in print mode (seen with a Slack plugin server).
- `--allowedTools` takes several values and swallows a trailing prompt argument; pass the prompt on stdin.
- The Arch `openai-codex` 0.153.4 refuses `gpt-6.1-sol`; npm `@openai/codex` 0.162.0 accepts it.
- A background Claude session that hits `API Error: Connection lost mid-response` stays alive and idle (`claude agents --json`: `status: idle`, `state: blocked`) and never retries or calls Triglav (seen 2026-10-15). The transcript line has `isApiErrorMessage: true`; telemetry does not count it as activity and stores it in `agent_sessions.transcript_error`. A Resume that finds the fork `busy` is skipped (the runner reports `ok: skipped: ...`); the card calls a launch that finished more than 2 minutes ago without a reconnect stuck (`web/src/resume-step.ts`) and its Restart session stops idle forks first (`stopIdleForks` in `scripts/runner.ts`). Left alone, such a session held host memory for days (seen 2026-10-19, 18 agents stuck this way, some over a week old): `reapAbandonedSessions` (`src/scheduler.ts` tick) now queues a `reap_session` launch for a claude-code session inactive past `POLICY.reapAgentSessionSec` (2 h), and the runner stops it (`claude stop`, conversation kept) without waiting for the Client to notice.
- `claude --bg` starts the first model turn before the MCP servers connect (the tools were announced 3.5 to 13.7 s after the prompt in the Staff transcripts, checked 2026-10-15). A call by the full name `mcp__orchestrator__get_guide` waits for the connection (one returned the guide at +3.05 s, before the tools were announced at +3.46 s); a model that looks for a short name `get_guide` finds none and may end its turn. That was never reliable: in 8 of the 32 starts with that prompt (2026-10-15 to 2026-10-18) the model did not make a call it could not see and ended the turn, and a probe told to call blind refused too. `staffStartPrompt` now has the first turn wait in Bash (`timeout 20 tail -f /dev/null`, again up to 3 times) before the call; a probe that waited 25 s had all 39 orchestrator tools. The session runs in a pre-started `claude bg-spare` process that does not inherit the runner's environment, so `CLAUDE_CODE_MCP_STARTUP_WAIT_MS` has no effect, and an allow rule for the tool in `--settings` did not make the first turn wait either (3 probes).
- A Claude session stopped by a usage limit keeps appending `queue-operation` lines; only model and tool lines count as activity.

## Conventions

- Match the surrounding code: short doc comments that say why, no speculative abstractions, SQL in the module that owns the table.
- Plain English in guide cards, prompts and dashboard copy. No em dashes.
- Commits: stage files by name (never `git add -A`), no attribution trailers, never force push. The maintainer merges; direct pushes to `main` are allowed in this repository.
