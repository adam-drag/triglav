# Local code review

Verified against the code on 2026-10-16 (RPP-B, the `sameCause` same-line rule; before that the evaluation harness, `scripts/review-eval/`; before that the PR review comment, `src/review-comment.ts`, and PR D: tuned prompt, chain of reviewed ranges, docs). If you find this out of date, fix it in the same PR. PR A built the server and runner module and the three tools; PR B (migration 034, `src/review-gate.ts`) made the review a gate; PR C (migration 035, `src/review-panel.ts`) made the panel the Client's setting and put the rounds on the job page; PR D (migration 036) tuned the prompt and closed the round-1 base gap.

## Flow

1. A Senior (holding an assignment) calls `request_code_review(worktree, base_sha, head_sha, notes)`. `requestCodeReview` (`src/code-review.ts`) validates (40-hex shas, absolute path, no secrets in notes), is idempotent for the same running range, refuses a second range while one runs, numbers the round inside the piece of work (`round_no`, see The gate), and runs `resolveSeats`. The Senior must hold an assignment with a live lease (the same fence as `report_progress`).
2. One `code_reviews` row, one `code_review_runs` row and one `launches` row (`kind 'code_review'`, `run_id` = the run id, `agent_id` = the Senior) per seat. Tables: `src/migrations/033_code_reviews.sql` (`code_reviews`, `code_review_runs`, `code_review_findings`).
3. `nextLaunch` -> `codeReviewLaunch`: marks the run `running` and returns ids, shas, model, effort and a **server-built prompt** (`buildReviewPrompt`, see The prompt; the ticket, criteria and PR notes are marked as data). The launch also carries `base_branch`, `expect_merge_base` and `expect_ancestor` (see The gate, chain). Never a command.
4. The runner (`codeReviewRun` in `scripts/runner.ts`) checks the fields, computes the diff itself (`worktreeDiff`: worktree must be at `head_sha`, no uncommitted tracked change, base present, and the merge base when `expect_merge_base` is set; `--unified=5`; a diff over `MAX_DIFF_CHARS` (250000) is refused, never cut), builds argv, runs the reviewer (`runReviewer`, which waits for `close` so no output is lost) with the prompt on stdin, keeps only the answer and usage lines of a Codex stream (`codexKeepLine`), fails the seat on kept output over 500000 characters, a JSON body over `MAX_REPORT_BYTES` (900000, Fastify's limit is 1 MB), a signal or the 20 min timeout, and posts `{code, stdout, stderr, secs}` to `POST /api/runner/:id/review-output` (runner key only, like every `/api/runner/*` route; no `OPEN_API_ROUTES` entry). A start failure goes through `/done failed:`, which fails the seat at once (`finishLaunch`).
5. `recordReviewOutput` parses (`parseReviewerOutput`), stores the seat, and when every seat has ended `finalizeIfDone` merges, writes `code_review_findings`, sets verdict and emits `code_review.finished`.
6. The Senior reads `get_code_review` and answers findings with `answer_finding` (valid, debatable, invalid, with a reason); the verdict is recomputed. `answer_finding` is a write: a Senior needs a live assignment on the job, Staff must be the job's Staff. It is refused once a later review exists (see The gate).

## The gate (`src/review-gate.ts`, migration 034)

- **Gate at a head.** `gateAt(conn, jobId, headSha)` passes when a finished (`status done`) review of exactly that sha has verdict `ok`. `submit_review_package` (`src/reviews.ts`, required `head_sha`, every review mode) and `request_copilot_review` refuse otherwise, with a reason (none, running, failed, `changes`). A review ends up `ok` by the seats finding no blocking issue, or by `answer_finding` clearing them.
- **Piece of work and rounds.** `workState` replays the job's finished reviews in `created_at, seq` order (migration 034 adds `code_reviews.seq`, auto increment, as the tiebreaker because `created_at` can tie; old rows got their `seq` in table order, so it alone is not their history). A review with verdict `ok` passes its head and ends the piece; others are rounds of the current piece. Failed and running reviews are never rounds. `round_no` is the round inside the piece. A review whose base is not the previous round's head starts its own piece (only old rows can; `requestCodeReview` refuses it).
- **The chain of reviewed ranges** (migrations 036 and 037, `code_reviews.base_branch`, `expect_merge_base` and `expect_ancestor`). Round 1 of a piece must start at the job's last passing head (`WorkState.lastPassingHead`) or at the merge base of the head with `origin/<job base_branch>`. The server cannot run git: when the base is not the last passing head (always the case for the first piece of a job), `requestCodeReview` sets `expect_merge_base` and the launch carries `base_branch`. `worktreeDiff` then runs `checkMergeBase` in the Senior's worktree: `refs/remotes/origin/<branch>` must exist (the runner never fetches; the reason says `git fetch origin <branch>`), `git merge-base head ref` must equal `base_sha`, otherwise the seat fails and the review is `failed` (not a round, ask again with the right base). A base branch that is not a plain name (`BASE_BRANCH`, duplicated in `src/code-review.ts` and `scripts/code-review-run.ts`) is refused by the server at request time and by the runner. When the base is the last passing head, `requestCodeReview` sets `expect_ancestor` instead and the runner's `checkAncestor` (`git merge-base --is-ancestor base head`) fails the seat after a reset or rebase, telling the Senior to use the merge base (a full re-review). Round 2 and later get neither check. `baseChecks` validates both launch flags and is tested. Old rows have both flags 0.
- **Request rules** (`requestCodeReview`): round 1 of a piece takes any base the chain allows (above); round 2 and later need `base_sha` = previous round's head (the fix delta) and every blocking finding of the previous round answered `valid` (invalid or a P2 debatable clears it). The new review stores `previous_review_id`; `codeReviewLaunch` passes that round's blocking findings to `buildReviewPrompt(previous)` as one marked-as-data section listing every blocking finding within a 60000-character budget (`previousList`: one line each, the first ones upgraded to full text while the budget lasts; the runner refuses a server prompt over 100000). `answerFinding` refuses a review once a later non-failed review exists, so verdicts, and with them the round count, cannot change retroactively.
- **Limit.** `LOCAL_ROUNDS` = 3 per piece; round 4 is refused with the text to raise a `failed_execution` blocker. `raiseBlocker` (a Senior, `failed_execution`) calls `noteRoundLimitBlocker`: when the piece is at its allowance it inserts `code_review_grants` (blocker id, `piece_first_review_id`, 3 rounds, `granted_at` null); `resolveBlockerTx` calls `grantRoundsFor`, which sets `granted_at`. The allowance of a piece is 3 plus its granted rows. A failed_execution blocker below the limit is not tied to anything.
- **Copilot rounds** (`copilot_rounds`, one row per round, unique per job + PR + round): `requestCopilotReview(assignmentId, attempt, pr, headSha)` needs a live lease (`requireAttempt`) and refuses without a passing gate on that head, when `COPILOT_ROUNDS` (3) are used, when the last round has no recorded result, recommended approval, had no qualifying finding (`qualifying` = P0+P1+P2 minus `previously_missed`), or has the same head. `recordCopilotResult` stores approval, P0-P3 counts and `previously_missed` (cannot exceed P0+P1+P2). The server cannot run `gh` and Seniors have it: the counts are the Senior's report, and the Copilot gate is a bar, not a boundary.
- **Test helper:** `passGate(ctx, jobId, requestedBy, head)` in `test/helpers.ts` inserts a done, `ok` review so a test can submit a package or request Copilot without running seats.

## Seats

**The panel is the Client's setting (PR C).** `settings` row `review_panel` (migration 035 widens `settings.value` to TEXT) holds `{strong:{runtime,model,effort}, cheap:[0..4 same]}`. `loadPanelConfig` (`src/code-review.ts`) reads it, and `requestCodeReview` calls it inside the request transaction, so a review that is running keeps the seats it started with (its `code_review_runs` rows). No row, or a row that does not parse, means `DEFAULT_PANEL`. `panelSeats(config)` names the seats: `strong`, then `cheap-<family>` with `-2`, `-3` for a later cheap seat of the same family (unique by construction; the default panel has exactly these names, a test checks it). `src/review-panel.ts`: `validatePanel` (one strong seat, a cheap list of at most `MAX_CHEAP_SEATS` = 4, runtime `claude-code` or `codex`, `SAFE` names, and `checkAgainstCatalog` from `src/models.ts`, so a model or effort outside the runner's list is refused when the report is fresh, and anything safe passes when no list is known), `setReviewPanel` (emits `review_panel.changed`, actor `client`, not a Staff wake type), `resetReviewPanel` (deletes the row, emits the same event with `reset: true`), `reviewPanelView`. Routes (Client session only, not in `OPEN_API_ROUTES`): `GET` and `PUT /api/review-panel`, `POST /api/review-panel/reset`. `resolveSeats` and its fallbacks are unchanged.

`DEFAULT_PANEL` (Client decision 2026-10-15): `strong` = codex `gpt-6.1-sol` high, `cheap-claude` = claude-code `claude-sonnet-5-5` low. A `cheap-codex` seat (codex `gpt-6-luna` low) was removed from the default on 2026-10-15 after the replay (see Measured); a saved panel can still add one, and `SEAT_FALLBACK.cheap.codex` stays for a cheap seat moved to Codex. `resolveSeats` (pure, tested): Codex is usable when the runner reports it and `codexUsedNow` < 90; Claude when reported. The strong seat prefers the family other than the Senior's own runtime. An unusable seat runs on the other CLI with `SEAT_FALLBACK` models (strong: claude-opus-5-5 high), a model missing from the runner's list is replaced the same way, and a seat identical to an earlier one is dropped (recorded in `summary.dropped`). Each seat stores `runtime`, `family`, `model`, `effort`, `note`; `get_code_review` shows `same_family` when one family covers every seat. No runtime at all: the review is `failed`, an `external` blocker is raised (actor `code-review`) and the event is sent. A model the CLI does not list is replaced by the seat's fallback on the same CLI, then by the other CLI's fallback, and otherwise the seat is dropped.

## The prompt (`buildReviewPrompt`, PR D)

Copilot's workflow as numbered steps: questions from the diff; a mandatory search of the repository for callers and sibling code paths, reading only the ranges needed (the cheap seats barely read the repository with the plain baseline prompt, so the search is a required step, not a hint); the repository rules (AGENTS.md, CLAUDE.md, .github/copilot-instructions.md); the ticket, criteria and PR notes (what the Senior put in `notes`) checked against the diff; edge cases (null and empty, error paths, races, stale state, escaping); tests; verify, then one finding per pattern with all its sites; an empty list when nothing is wrong. The tools named differ by runtime (Read, Grep and Glob for Claude, shell read commands for Codex). The task section (ticket, criteria, notes, previous-round findings) is marked as data. `test/code-review.test.ts` checks each step, their order and the size; the server prompt must stay under `MAX_SERVER_PROMPT_CHARS` and the previous-findings list under `PREVIOUS_BUDGET`.

Measured (replay on five private PRs at the head of Copilot's first review, 2026-10-15, one run per cell, so a small sample): the strong seat caught 7 of Copilot's 14 round-1 findings with the plain prompt and 7 with this prompt, at about 2.4 times the time (339 s to 808 s over 5 runs) and 2.1 times the input tokens (2.3M to 4.9M). The cheap Claude seat went from 0 to 1 caught and the cheap Codex seat stayed at 0, with 1 valid extra of 1 (Claude) and 1 valid of 5 (Codex). Do not read more into it than that.

## Reviewer command (`scripts/code-review-run.ts`)

- Claude: `claude -p --tools Read,Grep,Glob --allowedTools Read,Grep,Glob --permission-mode dontAsk --strict-mcp-config --mcp-config {"mcpServers":{}} --setting-sources user --settings {"disableAllHooks":true} --disable-slash-commands --no-session-persistence --output-format json --json-schema <schema>`; env `ENABLE_CLAUDEAI_MCP_SERVERS=false`. No Bash, so the diff is in the prompt. The two settings flags keep the reviewed repository's hooks from running (checked 2026-10-15: without them a project hook ran under `claude -p`).
- Codex: `codex exec --skip-git-repo-check --json -s read-only -c approval_policy="never" -m -c model_reasoning_effort --disable hooks --disable plugins <every MCP server off> --output-schema <private file> -C <cwd> -`. `codexMcpDisableAllArgs` (`scripts/research-run.ts`) switches off every server of `codex mcp list --json`, the orchestrator too. **No `--ephemeral`**: telemetry reads the Codex plan window from session files, so an ephemeral run would be invisible to the budget guard.
- `codex review` is not used (spike, codex-cli 0.162.0): it refuses a prompt together with `--base`/`--commit`, a custom prompt only adds to its built-in one, and it prints no JSON or usage.
- Env is `staffStartEnv(process.env)`: no Triglav secret reaches a reviewer, and it has no session token.

## Output handling (untrusted)

`parseReviewerOutput(runtime, stdout, cwd)`: Codex = JSONL, last `agent_message` text, usage summed over `turn.completed`; Claude = JSON envelope, `structured_output` or `result` text, usage and `total_cost_usd`. The answer must be `{findings: [...]}`; each finding is validated alone (severity P0-P3, title <= 200, body <= 4000), bad ones are dropped and counted in `rejected`, never repaired. Caps: 100 findings, 20 sites each; control characters removed; sites must be relative paths inside the worktree (no `..`, no absolute path elsewhere). Text is stored and shown as data, never executed.

## Merge and verdict

`mergeFindings` (built on `clusterFindings`, which the harness also uses to count duplicates by member): deterministic clustering, first match against the lead (most severe) finding of each cluster. `sameCause` says two findings are one defect when any of these holds: titles alike (Jaccard >= 0.6); sites within 5 lines of one file (line 0 counts as near) and title+body Jaccard >= 0.25; one file and title Jaccard >= 0.4; or (RPP-B, `sameLineSameWords`) they share an **exact** file and line and, on stemmed words (a plural s, a trailing `ed` and the doubled consonant it leaves are cut; other endings such as `ing` are not), the titles or title+body share at least 2 words and at least 0.4 of the smaller word set (overlap coefficient, `SAME_LINE_SHARE`, `SAME_LINE_SHARED`). The last rule exists because two seats word one defect differently, so Jaccard stays low while the line and a few key words agree. The line must be exact on purpose: on the stored baseline, findings of different defects sit one or two lines apart with 0.36 overlap, and the related PR 6 pair (a wider Cancel pattern and the narrower Cancel-button finding, two lines apart) must stay two findings. The merged finding has the union of sites, the highest severity, the text of its most severe report (with equal severity, the first in input order), and the seats that raised it. Thresholds are tuned on the stored baseline (two true pairs, a handful of near misses), so they are a small-sample fit: the margin is 0.47 and 0.5 against 0.25 at most for same-line non-pairs. Measured with `node scripts/review-eval/cli.ts merge` on the stored 2026-10-16 baseline of Triglav PRs 3, 6 and 8: before RPP-B it merged nothing (8 to 8, 8 to 8, 4 to 4, 2 of 2 judged duplicates left apart); now PR 8 is 8 to 6 (the late-Staff registration finding, P1, and the failure-writes-no-event finding, P2, each merged into one finding naming both seats), PR 6 and PR 3 are unchanged, and 0 of 2 judged duplicates are left apart. No catch or partial finding is lost (a test checks each is inside a merged finding of its seat). On the 2026-10-15 baseline outputs (private PRs) the old rules merged nothing wrongly; the new rule was not run on that data, which is not in the repository.

`blocks(finding)`: P0/P1 block unless triaged `invalid`; P2 blocks until triaged `debatable` or `invalid`; P3 never. A `valid` triage does not clear anything: a fix is a new head sha and a new review. `verdict` is `ok` or `changes`; any failed, timed-out or unparseable seat makes the review `failed`, which never passes. Failed seats do not raise blockers; the guide says retry once, then raise one. `timeoutReviewRuns` (scheduler tick) fails a running seat 25 min after it started (`started_at`, so a late pick-up still gets the runner's 20 min) and a queued seat 25 min after the request; `expireStaleLaunches` drops unpicked launches after 10 min, one conditional update per launch. A failed review lists no blocking finding (its findings stay visible).

## Job page view

`jobReviewsView(conn, jobId)` (`src/code-review.ts`), served at `GET /api/jobs/:id/reviews` (Client session; separate from `getJob` so agents' `get_job` does not carry reviewer text): every `code_reviews` row of the job in request order (running and failed too) as `reviewView` plus `created_at`, `finished_at`, `wall_secs` and summed `cost_usd`, and the `copilot_rounds` rows. The dashboard (`CodeReviews` in `web/src/App.tsx`) renders every string from it as plain text.

## The PR comment (`src/review-comment.ts`)

One comment per PR with the local review rounds, so a reader of the PR sees what the local gate did. The server builds the text; the Senior posts it. MCP tool `get_review_comment(job_id, head_sha)` (`getReviewComment`, READ, untrusted notice): a Senior with a live assignment on the job (held, lease not expired) or the job's Staff, refused unless `gateAt(job, head_sha)` passes. Returns `{job_id, head_sha, gate_review_id, marker, rounds, chars, body}`. The guide step is the last section of `src/guide/deliver.md` ("Triglav review comment"), pointed at from `senior.md` steps 6 and 8: `get_review_comment`, write the body to a file, find the Senior's comment by its marker (`gh api repos/<repo>/issues/<pr>/comments`, first line of the body), `gh pr comment <pr> --body-file` once, later `gh api -X PATCH repos/<repo>/issues/comments/<id> -F body=@<file>`. Never a second comment. The server cannot run `gh`, so this is a bar, not a boundary.

- `buildReviewComment` reads every `code_reviews` row of the job with status `done` or `failed` (running is skipped) in `created_at, seq` order and renders `reviewView` of each (`renderReviewComment`, pure, tested without a database). First line is the marker `<!-- triglav-local-review job=<job_id> -->`. Per round: shas (12 chars), verdict or failure reason, seats (runtime, model, effort, secs, tokens in/cached/out, cost or `n/a`), merged findings (severity, title, up to 5 sites, seat count, triage and reason). No finding body, no link, no dashboard address.
- Untrusted text goes through `codeSpan`: control, format and line-separator characters and newlines collapse to a space, text is cut at 300 characters, and the fence is one backtick longer than the longest backtick run in the text (a space pads a text that starts or ends with a backtick). Only fixed text, numbers and shas are outside a span. `assertNoSecrets` runs on the whole body; a hit refuses the comment.
- Size: `MAX_COMMENT_CHARS` = 60000 (GitHub allows 65536). When over, older rounds shrink to one line (counts per severity), then the newest round's findings are cut (100, 50, 20, 10, 5, 0), then the oldest lines are dropped with a count.
- Tests: `test/review-comment.test.ts` (code span, hostile text per field, marker, cap, card commands, tool auth, gate refusal, secret refusal).
- Known limit, not part of this change: `reviewView` and `finalizeIfDone` sort rows that hold large JSON, and MySQL's sort buffer failed with "Out of sort memory" in `finalizeIfDone` in a test with 100 findings of 20 sites each (paths of about 130 characters). Seen once, not investigated.

## Evaluation harness (`scripts/review-eval/`)

Dev only, by hand. Measures the panel against Copilot's findings on Triglav's own PRs; nothing in it runs in CI, in the Docker image (the Dockerfile copies `src` and `web`) or from a package script, and a test checks all three. Entry: `node scripts/review-eval/cli.ts list | score | merge | run` (README, "Evaluating the review panel").

- **Files.** `data.ts` (zod schemas and loaders for fixtures, stored runs and judgments, `checkJudgments`), `score.ts` (pure scorer and table), `merge.ts` (production `mergeFindings` over a stored run, and `duplicatesAfterMerge`, which counts the judged duplicates the clustering still keeps in two clusters, by seat and index), `run.ts` (the live path), `cli.ts` (`refuseInCi`, commands).
- **Live path.** `run.ts` builds nothing of its own: `worktreeDiff`, `buildReviewPrompt` + `reviewPrompt`, `claudeReviewArgs` / `codexReviewArgs`, `runReviewer`, `reviewerReport`, `parseReviewerOutput` and `staffStartEnv`, so a seat has the runner's access and no Triglav secret. `REVIEW_STDOUT_MAX` and `REVIEW_TIMEOUT_MS` are copies of the constants in `scripts/runner.ts` (a test compares them). `run` needs `--yes`, refuses when `CI` is set, writes raw output under `review-eval-out/` (git-ignored) and keeps a finished fixture of an arm, so a rerun never pays twice. It does not check the Codex or Claude plan limits. A failed seat is stored with `error` and no findings, and the scorer counts it as failed.
- **Data** (`test/fixtures/review-eval/`). `prs/<id>.json`: PR, full base and head sha (the head of Copilot's first review), title and the PR description cut before anything written after the review, and per Copilot finding `id` (`<fixture>-r<round>-<letter>`), round, severity (Copilot's own `high`, `medium`, `low`, never mixed with P0-P3), file, line and a label in our own words. Never copy Copilot's text, and nothing from a private repository (a test greps for it). A finding of round 2 or later carries `ceiling` (true when the code was already wrong at the round 1 head) and `ceiling_basis`. `runs/<arm>/<id>.json`: the stored seat output. `judgments/<arm>.json`: per panel finding `seat#index`, its title (checked against the run), and `catch` (same cause and fix, names the Copilot id), `partial`, `valid`, `invalid` or `unsure`, plus `dup_of` for a repeat of another finding. A finding with no judgment counts as unjudged.
- **Scoring** (plan section 7.4, `docs/plans/review-panel-parity.md` while it exists). Per fixture, in total and per seat: R1 recall, ceiling recall, valid extras, noise (`invalid` only), unjudged (`unsure` or missing, always printed beside noise, which is a floor), dup, partial, finding count, input tokens with the cached ones apart (Codex's `tokensIn` already holds its cached tokens, Claude's does not, so `seatInput` adds them), output tokens, wall seconds (slowest seat) and seat seconds, and Claude's cost (Codex reports none, so `n/a`).
- **Baseline.** `runs/baseline` and `judgments/baseline.json`: the default panel on PRs 3, 6 and 8, one run per seat, scored by one reader who knew the seat. It scores 7 of 12 round 1 findings (strong 7, cheap-claude 3), ceiling 10 of 17, 20 findings, 3 valid extras, 0 noise, 3 unjudged, 2 duplicates (the PR 8 pairs) and 1 partial. The PR 8 seats were given a description that already listed the fixes to Copilot's round 1 findings; the fixture now cuts it, so a new run of PR 8 is not comparable with the baseline. PR 6's description reached the seats cut at 4000 characters, before its Copilot section. One run per cell: a difference of one or two findings is not a result.

## Event

`code_review.finished` (payload: review_id, job_id, head_sha, status, verdict, failure, findings counts) is emitted with `jobId: null` and `targets: [the Senior]`, so an `owned` read matches only the Senior. It is not in `STAFF_WAKE_TYPES`; do not add it.
