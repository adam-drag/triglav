## Flow

1. A Senior (holding an assignment) calls `request_code_review(worktree, base_sha, head_sha, notes)`. `requestCodeReview` (`src/code-review.ts`) validates (40-hex shas, absolute path, no secrets in notes), is idempotent for the same running range, refuses a second range while one runs, numbers the round inside the piece of work (`round_no`, see The gate), and runs `resolveSeats`. The Senior must hold an assignment with a live lease (the same fence as `report_progress`).
2. One `code_reviews` row, one `code_review_runs` row and one `launches` row (`kind 'code_review'`, `run_id` = the run id, `agent_id` = the Senior) per seat. Tables: `src/migrations/033_code_reviews.sql` (`code_reviews`, `code_review_runs`, `code_review_findings`).
3. `nextLaunch` -> `codeReviewLaunch`: marks the run `running` and returns ids, shas, model, effort and a **server-built prompt** (`buildReviewPrompt`, see The prompt; the ticket, criteria and PR notes are marked as data). The launch also carries `base_branch`, `expect_merge_base` and `expect_ancestor` (see The gate, chain). Never a command.
4. The runner (`codeReviewRun` in `scripts/runner.ts`) checks the fields, computes the diff itself (`worktreeDiff`: worktree must be at `head_sha`, no uncommitted tracked change, base present, and the merge base when `expect_merge_base` is set; `--unified=5`; a diff over `MAX_DIFF_CHARS` (250000) is refused, never cut), builds argv, runs the reviewer (`runReviewer`, which waits for `close` so no output is lost) with the prompt on stdin, keeps only the answer and usage lines of a Codex stream (`codexKeepLine`), fails the seat on kept output over 500000 characters, a JSON body over `MAX_REPORT_BYTES` (900000, Fastify's limit is 1 MB), a signal or the 20 min timeout, and posts `{code, stdout, stderr, secs, ranges?}` (see Location label and resolved list) to `POST /api/runner/:id/review-output` (runner key only, like every `/api/runner/*` route; no `OPEN_API_ROUTES` entry). A start failure goes through `/done failed:`, which fails the seat at once (`finishLaunch`).
5. `recordReviewOutput` parses (`parseReviewerOutput`), stores the seat, and when every seat has ended `finalizeIfDone` merges, writes `code_review_findings`, sets verdict and emits `code_review.finished`.
6. The Senior reads `get_code_review` and answers findings with `answer_finding` (valid, debatable, invalid, with a reason); the verdict is recomputed. `answer_finding` is a write: a Senior needs a live assignment on the job, Staff must be the job's Staff. It is refused once a later review exists (see The gate).

## The gate (`src/review-gate.ts`, migration 034)

- **Gate at a head.** `gateAt(conn, jobId, headSha)` passes when a finished (`status done`) review of exactly that sha has verdict `ok`. `submit_review_package` (`src/reviews.ts`, required `head_sha`, every review mode) and `request_copilot_review` refuse otherwise, with a reason (none, running, failed, `changes`). A review ends up `ok` by the seats finding no blocking issue, or by `answer_finding` clearing them.
- **Piece of work and rounds.** `workState` replays the job's finished reviews in `created_at, seq` order (migration 034 adds `code_reviews.seq`, auto increment, as the tiebreaker because `created_at` can tie; old rows got their `seq` in table order, so it alone is not their history). A review with verdict `ok` passes its head and ends the piece; others are rounds of the current piece. Failed and running reviews are never rounds. `round_no` is the round inside the piece. A review whose base is not the previous round's head starts its own piece (only old rows can; `requestCodeReview` refuses it).
- **The chain of reviewed ranges** (migrations 036 and 037, `code_reviews.base_branch`, `expect_merge_base` and `expect_ancestor`). Round 1 of a piece must start at the job's last passing head (`WorkState.lastPassingHead`) or at the merge base of the head with `origin/<job base_branch>`. The server cannot run git: when the base is not the last passing head (always the case for the first piece of a job), `requestCodeReview` sets `expect_merge_base` and the launch carries `base_branch`. `worktreeDiff` then runs `checkMergeBase` in the Senior's worktree: `refs/remotes/origin/<branch>` must exist (the runner never fetches; the reason says `git fetch origin <branch>`), `git merge-base head ref` must equal `base_sha`, otherwise the seat fails and the review is `failed` (not a round, ask again with the right base). A base branch that is not a plain name (`BASE_BRANCH`, duplicated in `src/code-review.ts` and `scripts/code-review-run.ts`) is refused by the server at request time and by the runner. When the base is the last passing head, `requestCodeReview` sets `expect_ancestor` instead and the runner's `checkAncestor` (`git merge-base --is-ancestor base head`) fails the seat after a reset or rebase, telling the Senior to use the merge base (a full re-review). Round 2 and later get neither check. `baseChecks` validates both launch flags and is tested. Old rows have both flags 0.
- **Request rules** (`requestCodeReview`): round 1 of a piece takes any base the chain allows (above); round 2 and later need `base_sha` = previous round's head (the fix delta) and every blocking finding of the previous round answered `valid` (invalid or a P2 debatable clears it). The new review stores `previous_review_id`; `codeReviewLaunch` passes that round's blocking findings to `buildReviewPrompt(previous)` as one marked-as-data section listing every blocking finding within a 60000-character budget (`previousList`: one line each, the first ones upgraded to full text while the budget lasts; the runner refuses a server prompt over 100000). `answerFinding` refuses a review once a later non-failed review exists, so verdicts, and with them the round count, cannot change retroactively.
- **Limit.** `LOCAL_ROUNDS` = 3 per piece; round 4 is refused with the text to raise a `failed_execution` blocker. `raiseBlocker` (a Senior, `failed_execution`) calls `noteRoundLimitBlocker`: when the piece is at its allowance it inserts `code_review_grants` (blocker id, `piece_first_review_id`, 3 rounds, `granted_at` null); `resolveBlockerTx` calls `grantRoundsFor`, which sets `granted_at`. The allowance of a piece is 3 plus its granted rows. A failed_execution blocker below the limit is not tied to anything.
- **Copilot rounds** (`copilot_rounds`, one row per round, unique per job + PR + round): `requestCopilotReview(assignmentId, attempt, pr, headSha)` needs a live lease (`requireAttempt`) and refuses without a passing gate on that head, when `COPILOT_ROUNDS` (3) are used, when the last round has no recorded result, recommended approval, had no qualifying finding (`qualifying` = P0+P1+P2 minus `previously_missed`), or has the same head. `recordCopilotResult` stores approval, P0-P3 counts and `previously_missed` (cannot exceed P0+P1+P2). The server cannot run `gh` and Seniors have it: the counts are the Senior's report, and the Copilot gate is a bar, not a boundary.
- **Test helper:** `passGate(ctx, jobId, requestedBy, head)` in `test/helpers.ts` inserts a done, `ok` review so a test can submit a package or request Copilot without running seats.

## Location label and resolved list (PR F, migration 039)

Both are extras of a round 2 or later. Neither is read by `blocks`, `verdictOf`, `workState`, `answerFinding` or the chain; `test/review-ranges.test.ts` and `test/code-review-flow.test.ts` check that blocking, the verdict and the round count are the same with and without them.

- **Changed ranges** (`src/review-ranges.ts`, pure, imported by the server and the runner). `worktreeDiff` returns `{diff, ranges}`: `changedRanges(diff)` reads the same diff (now made with `--no-color --src-prefix=a/ --dst-prefix=b/`, so user git config cannot change the headers) into `[{file, ranges: [[start, end]]}]` of the new side. Hunks are read by their line counts, so file content that looks like a header is never a header. A removal with nothing added marks the lines around it; deleted, binary and renamed-only files have no range; quoted paths are decoded. It returns null, never a part, when the diff cannot be read exactly or is over the caps (`MAX_RANGE_FILES` 1000, `MAX_RANGES_PER_FILE` 500, path 300, `MAX_RANGES_BYTES` 200000). `reviewerReport(r, ranges)` adds `ranges` to a successful report only when it fits under `MAX_REPORT_BYTES`.
- **Route.** `/api/runner/:id/review-output` (runner key only, as before) takes `ranges: z.unknown().optional()`. `recordReviewOutput` runs `parseRanges` (all or nothing: one bad entry or any cap drops the field) and stores the result in `code_review_run_deltas` (per run; a separate table so the sorts of `code_review_runs` rows stay as they were). A bad `ranges` or `resolved` never fails a run that has valid findings.
- **Label.** `finalizeIfDone` unions the ranges of the seats and sets `code_review_findings.outside_delta` (TINYINT, null/0/1) with `outsideDelta(sites, ranges)`: 1 when no site of the merged finding is on a changed line (a file the diff did not touch counts as outside; a site at line 0 is inside when the file has any changed line), 0 when one is, null for round 1 (`previous_review_id` is null), when no seat posted valid ranges, or when the finding has no site. It is a location label only: a changed caller can make a defect show at an unchanged callee, so outside does not mean "was already there". Nothing is called "previously missed" (that needs evidence the server does not have; see docs/plans/review-panel-parity.md O7a). The prompt still tells reviewers not to report what the diff did not touch.
- **Resolved list.** A round 2+ launch with findings to answer has `answers_resolved: true`; the prompt lists each previous finding as `[id <finding id>]` (the id survives the budget cut) and asks for `resolved: [{id, status: fixed|not_fixed|unknown, sites}]` (only listed ids, once each; `unknown` when the code read does not settle it); the runner picks `reviewSchemaJson(runtime, true)`: optional for Claude, a required key for Codex (checked 2026-10-16: Codex's structured output refuses a schema whose `required` omits a property, so an empty list is the "nothing" answer there). `parseReviewerOutput` reads it per item like findings (`ParsedOutput.resolved`; a bad item is dropped, cap 300; an id that appears more than once anywhere in the raw list, bad or past the cap included, is dropped in every entry; only ids, an enum and sites, no free text) and counts what it dropped in `resolvedDropped` (a non-list, null included, counts 1; an absent field is no answer). `recordReviewOutput` asks `findingsToAnswer` (the blocking findings of `previous_review_id`, the same list the prompt had) and `checkResolved` drops ids not on it and every entry of a repeated id, adding them to the count; it stores `resolved_dropped` (round 2+ only) in `code_review_run_deltas`. `finalizeIfDone` writes a `code_review_resolutions` row for every asked id (`mergeResolved(asked, perSeat)`): `not_fixed` if any seat says so; else `unknown` if any seat says unknown or no seat answered; `fixed` only when every answering seat says fixed. `unknown_by` and `silent` (seats with no answer for that id) are stored too. The status is advisory, apart from the Senior's triage on `code_review_findings`: it never changes `blocks()`, the verdict or the gate.
- **Reading.** `reviewView` (so `get_code_review` and the job page) has `outside_delta` per finding and `resolved` per review (previous finding id, its severity and title, status, sites, `fixed_by`, `not_fixed_by`, `unknown_by`, `silent`), and `resolved_dropped` per seat. The dashboard shows both as plain text. The PR comment (`src/review-comment.ts`) is unchanged and does not show them.


## Provenance and incomplete output (migration 040)

- **Provenance.** `recordReviewOutput` keeps each seat's parsed findings in `code_review_runs.findings_json` as before. `finalizeIfDone` passes `run_id` and `index` (position in that list) on each `SeatFinding`; `mergeFindings` returns `sources` (`{run_id, seat, index, severity}` per report in the cluster) and `omitted_sites` (distinct sites past `MAX_SITES`, 20), stored on `code_review_findings`. `reviewView` resolves each source to its own `title`, `body` and `sites` from `findings_json` (null text for rows stored before provenance). Clustering is not transitive: a report joins only when it matches the cluster's lead (tested both ways).
- **Requested model.** `requestCodeReview` stores the panel's `requested_runtime`, `requested_model` and `requested_effort` on each run (from the saved panel entry of that seat). `reviewView` shows `requested` per seat (null on older rows) next to the effective runtime, model and effort.
- **Incomplete output (Client decision 2026-10-17, interim).** `reviewView` has per seat `rejected` (parser) and `zero_site` (findings in `findings_json` with no valid site), and `incomplete: {seats, zero_site_findings} | null`. The job page shows a warning with the per-seat counts and the zero-site findings. It never says complete or verified. The verdict and the gate are unchanged; stricter handling is an open policy decision.
## Repository rules (migration 043)

The runner reads the reviewed repository's written rules with git and puts them in each seat's stdin as data, between the server prompt and the diff (`reviewPrompt(..., rules.section)`); the server never sees the text. `scripts/review-rules.ts`, called by `codeReviewRun` in `scripts/runner.ts` after `worktreeDiff`:

- **Commit.** `rulesCommit`: merge base of head with `refs/remotes/origin/<base_branch>`, else with `refs/heads/<base_branch>`, else the round's `base_sha` (source `origin`, `local`, `base_sha`). Never fetches. `codeReviewLaunch` sends `base_branch` on every round (null when it fails `BASE_BRANCH`); a non-plain string is refused by the runner. `repositoryRules` falls to `base_sha` when the tree at the first commit cannot be read; it throws (the seat fails) only when no source can be read. Round 2+ still read at the merge base, so a rule edit of round 1 is not "base" there; only the `base_sha` fallback of round 2+ is the previous round's head, which already holds earlier rounds' rule edits (the prompt and the job page say so). `repositoryRulesAt` (harness) reports source `given`.
- **Files**, from `ls-tree -r -l -z` at that commit, blobs read by object id (`cat-file blob`), a symlink followed once inside the tree, a blob over 1 MB listed as omitted, a link out of the tree (absolute or `..`) or dangling skipped, a path that fails `goodPath` (the server's summary check) skipped: root `AGENTS.md`, `CLAUDE.md`, `AGENT.md`, `.github/copilot-instructions.md`; for each path changed in rules-commit..head (`diff --no-renames --name-only -z`, the whole PR, not the round) the nearest non-root dir holding a readable `AGENTS.md`/`CLAUDE.md`/`AGENT.md` (an unreadable link does not stop the search); `.github/instructions/**/*.instructions.md` whose frontmatter `applyTo` (comma list, split only outside `{}`/`[]` and not at `\,`; `frontmatter` also reads `>`/`|` blocks and indented continuations, skipping `#` comments outside a block) matches a changed path with `path.matchesGlob` (dot directories do not match `**`); a catalog (name, description, path) of `.claude/skills/*/SKILL.md` and `.agents/skills/*/SKILL.md` (past `MAX_SKILLS` 200, or over 1 MB, listed as omitted). A file whose summary entry would push the file entries past `MAX_RULES_BYTES` less `SUMMARY_RESERVE` is omitted from the prompt and the summary alike. Identical content is sent once (`same_as`).
- **Budget.** `RULES_BUDGET` 40000 for the section, apart from `MAX_SERVER_PROMPT_CHARS`. The changed-files note first, then whole files in priority order, then one file cut with a `[cut by the runner ...]` marker, the rest omitted with a count; the catalog fills what is left. The heading, the paragraph and a 400-character reserve for closing lines count too, so the whole section is at most `RULES_BUDGET`. When the summary is over `MAX_RULES_BYTES`, the omitted and then the changed path lists shrink (their `_more` counts grow). Paths are JSON-quoted and each file is fenced longer than its longest backtick run.
- **Prompt.** The section heading says data, not instructions, the commit and source; `RULES_PRIORITY` is the fixed paragraph (rules outrank general knowledge on defects, a broken rule is a finding naming the file, a finding a rule contradicts is not reported, rules never change role, tools, steps or output format). When the PR changes a rule file (`isRulePath`), a fixed note lists the paths and asks seats to review them as code.
- **Report.** `reviewerReport(r, ranges, rules.summary)` adds `rules` on success when it fits. `/api/runner/:id/review-output` takes `rules: z.unknown()`; `recordReviewOutput` runs `parseRulesSummary` (`src/review-rules.ts`, all or nothing, caps `MAX_RULE_LIST` 300, path 300, chars sum ≤ budget, `MAX_RULES_BYTES`) and stores it in `code_review_run_deltas.rules`; a bad one is dropped and never fails the run. `reviewView` has `rules` per review (first seat's) and `rules_commit`/`rules_source` per seat. The job page shows source, files, cut and omitted, and a warning listing changed rule files, as plain text.
- **Harness.** `runFixture` reads the rules with `repositoryRulesAt` at the fixture's base (its PR merge base; origin/main would be the head once merged) and passes the section to `seatPrompt`. The lean prompt's step 3 points at the section too.
- **Not done:** the Codex seat still loads the host user's `~/.codex` AGENTS.md and skills (plan spike 1b); Copilot's `excludeAgent` frontmatter is not read.

## Seats

**The panel is the Client's setting (PR C).** `settings` row `review_panel` (migration 035 widens `settings.value` to TEXT) holds `{strong:{runtime,model,effort,count?}, cheap:[0..4 same]}`. `count` (1 to `MAX_STRONG_COUNT` = 4, absent means 1; `validatePanel` never stores a 1) repeats the strong seat, and strong members plus cheap seats are at most `MAX_PANEL_SEATS` = 6 (`validatePanel` and the `StoredPanel` refine; a stored row over the bound does not parse and reads as the default). Only `PUT /api/review-panel` (Client session) sets it; no MCP tool does. `loadPanelConfig` (`src/code-review.ts`) reads it, and `requestCodeReview` calls it inside the request transaction, so a review that is running keeps the seats it started with (its `code_review_runs` rows). No row, or a row that does not parse, means `DEFAULT_PANEL`. `panelSeats(config)` names the seats: `strong` (and `strong-2`, `strong-3`, `strong-4` for repeat members, which carry `group: 'strong'`), then `cheap-<family>` with `-2`, `-3` for a later cheap seat of the same family (unique by construction; the default panel has exactly these names, a test checks it). `src/review-panel.ts`: `validatePanel` (one strong seat, a cheap list of at most `MAX_CHEAP_SEATS` = 4, runtime `claude-code` or `codex`, `SAFE` names, and `checkAgainstCatalog` from `src/models.ts`, so a model or effort outside the runner's list is refused when the report is fresh, and anything safe passes when no list is known), `setReviewPanel` (emits `review_panel.changed`, actor `client`, not a Staff wake type), `resetReviewPanel` (deletes the row, emits the same event with `reset: true`), `reviewPanelView` (also `max_strong_count`, `max_panel_seats` and `averages`: `seatAverages` is the mean input (`tokens_in`, plus `tokens_cached` for Claude runs, since Codex counts cached tokens inside input and Claude apart) and `tokens_out` of `done` runs per runtime, model and effort; the Models page turns them into the expected tokens of a review with `expectedTokens` in `web/src/panel-tokens.ts`, per member, falling back to the same model at another effort, leaving out a seat with no data and a cheap seat that repeats an earlier cheap seat, which resolveSeats always drops; a cheap seat equal to a strong member is kept, because the strong seat may move to the other CLI). Routes (Client session only, not in `OPEN_API_ROUTES`): `GET` and `PUT /api/review-panel`, `POST /api/review-panel/reset`. `resolveSeats` and its fallbacks are unchanged.

**File order of the repeat members (RPP-E, `scripts/code-review-run.ts`).** `strong-2` and later read the diff's file blocks in a seeded order; `strong`, every cheap seat and a panel with count 1 read the diff as git printed it. `codeReviewLaunch` sends the seat name as `seat`; the runner passes it with the head sha to `diffForSeat(diff, seat, head)`, which checks it (`SEAT_NAME`, 40 characters at most; a bad one fails the seat, an absent one from an older server means no reorder) and reorders only when `REPEAT_MEMBER` matches (`strong-2` to `strong-99`). `seededFileOrder(diff, seed)` is pure: `splitDiffFiles` splits on `diff --git ` headers while it reads hunks by their line counts (as `changedRanges` does) and returns null when the diff does not split exactly (no leading header, no final newline, a hunk that is cut short, a hunk line with another prefix), and then the original order is used; after that comes a Fisher-Yates shuffle with mulberry32 seeded by the SHA-256 of `<seat>\n<head sha>`; when the shuffle leaves the original first block first (Copilot round 1 on PR 27: one chance in two with two files), it is swapped with a seeded other block, so the first file always differs from the unshuffled seat's. Blocks stay whole (hunk order, rename, mode and binary headers, `\ No newline` lines), so the output is a permutation of the input blocks. It runs in `codeReviewRun` after `worktreeDiff`, so the `MAX_DIFF_CHARS` check and the changed ranges belong to the original diff (a permutation changes neither). The harness uses the same function: `seatPrompt` in `scripts/review-eval/run.ts` calls `diffForSeat` with the fixture's head. Restart the runner after a change here. Tests: `test/code-review-diff-order.test.ts` (no database); the launch field is checked in `test/code-review-flow.test.ts` and `test/review-panel.test.ts`.

`DEFAULT_PANEL` (Client decisions 2026-10-15 and 2026-10-20): `strong` = codex `gpt-6.1-sol` high, `cheap-claude` = claude-code `claude-sonnet-5-5` low, `lens-contracts` and `lens-integrity` = claude-code `claude-haiku-5-5` medium, shadow on. A `cheap-codex` seat (codex `gpt-6-luna` low) was removed from the default on 2026-10-15 after the replay (see Measured); a saved panel can still add one, and `SEAT_FALLBACK.cheap.codex` stays for a cheap seat moved to Codex. `resolveSeats` (pure, tested): Codex is usable when the runner reports it and `codexUsedNow` < 90; Claude when reported. The strong seat prefers the family other than the Senior's own runtime. An unusable seat runs on the other CLI with `SEAT_FALLBACK` models (strong: claude-opus-5-5 high), a model missing from the runner's list is replaced the same way, and a seat identical to an earlier one is dropped (recorded in `summary.dropped`), except the members of one `group` (repeat members of the strong seat), which are meant to be identical. Every member is resolved alone, so each gets the Senior-family swap, the CLI fallback and the model fallback itself. Each seat stores `runtime`, `family`, `model`, `effort`, `note`; `get_code_review` shows `same_family` when one family covers every seat. No runtime at all: the review is `failed`, an `external` blocker is raised (actor `code-review`) and the event is sent. A model the CLI does not list is replaced by the seat's fallback on the same CLI, then by the other CLI's fallback, and otherwise the seat is dropped.

**Lens seats (migration 045).** The stored panel has an optional `lenses: [{runtime, model, effort, lens, shadow}]` (`StoredLens`; `LENSES` = `contracts`, `integrity`). A row without `lenses` (every row saved before) parses as before and runs no lens seat; `validatePanel` leaves the key out when the request has none. Lens seats count in `MAX_PANEL_SEATS` (`seatTotal`). `panelSeats` names them `lens-<lens>`, then `lens-<lens>-2`; `PanelSeat` has `kind: 'lens'`, `lens` and `shadow`. In `resolveSeats` the twin check also compares `lens`, so seats with different lenses (a generalist has none) both run and the same lens on the same runtime, model and effort is dropped; of two such twins the blocking one runs wherever it is in the panel, and the shadow one is dropped. A lens seat does not use the Senior-family swap or `SEAT_FALLBACK`: when its runtime is not usable or its model is not offered it takes the first usable and offered entry of `LENS_FALLBACK` (codex `gpt-6-luna` low, then claude-code `claude-sonnet-5-5` low; Client decision 2026-10-20), keeps lens and shadow, and the seat `note` says why; with no entry it is dropped. A resolution where only shadow seats are left is refused (`No blocking seat can run`). `code_review_runs.lens` and `.shadow` store both per run; `codeReviewLaunch` passes the lens to `buildReviewPrompt`. Seat order everywhere is `SEAT_ORDER` (strong, cheap, lens, then name).

**Shadow mode.** A merged finding has `shadow` (stored in `code_review_findings.shadow`) when every report in it came from a shadow seat. `clusterFindings` clusters the blocking seats' reports first, exactly as without shadow seats, then lets shadow reports join or start clusters, so a shadow report never changes the lead, severity or grouping of what blocks, and a finding a blocking seat also reported is not shadow and blocks as before. `blocks()` returns false for a shadow finding whatever its severity or triage, so it never counts in the verdict, the gate, the round 2+ `findingsToAnswer` list or the open-findings check of the next request; `answer_finding` accepts an answer to it and stores it, which changes nothing. In `finalizeIfDone` a failed or timed-out shadow seat is shown failed and does not fail the review; the review fails when a blocking seat failed or when no blocking seat finished. The event counts put shadow findings under `shadow`, not under their severity. Round limits, Copilot rounds and the chain are unchanged.

## The prompt (`buildReviewPrompt`, PR D)

Copilot's workflow as numbered steps: questions from the diff; a mandatory search of the repository for callers and sibling code paths, reading only the ranges needed (the cheap seats barely read the repository with the plain baseline prompt, so the search is a required step, not a hint); the repository rules (step 3 points at the runner's "Repository rules" section below, read at the base, not the head's files); the ticket, criteria and PR notes (what the Senior put in `notes`) checked against the diff; edge cases (null and empty, error paths, races, stale state, escaping); tests; verify, then one finding per pattern with all its sites; an empty list when nothing is wrong. The tools named differ by runtime (Read, Grep and Glob for Claude, shell read commands for Codex). The task section (ticket, criteria, notes, previous-round findings) is marked as data. A lens seat gets `lensSection(lens)` after step 7 and before the findings format: every step still applies (the search included), the repository rules outrank the lens, the lens checklist (`LENS_TEXT`), and silence is the normal answer, a finding needing a concrete failure path. In round 2+ a lens seat gets the same previous-findings section as the others. `test/code-review.test.ts` checks each step, their order and the size; the server prompt must stay under `MAX_SERVER_PROMPT_CHARS` and the previous-findings list under `PREVIOUS_BUDGET`.

Measured (replay on five private PRs at the head of Copilot's first review, 2026-10-15, one run per cell, so a small sample): the strong seat caught 7 of Copilot's 14 round-1 findings with the plain prompt and 7 with this prompt, at about 2.4 times the time (339 s to 808 s over 5 runs) and 2.1 times the input tokens (2.3M to 4.9M). The cheap Claude seat went from 0 to 1 caught and the cheap Codex seat stayed at 0, with 1 valid extra of 1 (Claude) and 1 valid of 5 (Codex). Do not read more into it than that.

- Codex: `codex exec --skip-git-repo-check --json -s read-only -c approval_policy="never" -m -c model_reasoning_effort --disable hooks --disable plugins <every MCP server off> --output-schema <private file> -C <cwd> -`. `codexMcpDisableAllArgs` (`scripts/research-run.ts`) switches off every server of `codex mcp list --json`, the orchestrator too. **No `--ephemeral`**: telemetry reads the Codex plan window from session files, so an ephemeral run would be invisible to the budget guard.

## Output handling (untrusted)

`parseReviewerOutput(runtime, stdout, cwd)`: Codex = JSONL, last `agent_message` text, usage summed over `turn.completed`; Claude = JSON envelope, `structured_output` or `result` text, usage and `total_cost_usd`. The answer must be `{findings: [...]}`; each finding is validated alone (severity P0-P3, title <= 200, body <= 4000), bad ones are dropped and counted in `rejected`, never repaired. Caps: 100 findings, 20 sites each; control characters removed; sites must be relative paths inside the worktree (no `..`, no absolute path elsewhere). Text is stored and shown as data, never executed.

## Merge and verdict

`mergeFindings` (built on `clusterFindings`, which the harness also uses to count duplicates by member): deterministic clustering, first match against the lead (most severe) finding of each cluster. `sameCause` says two findings are one defect when any of these holds: titles alike (Jaccard >= 0.6); sites within 5 lines of one file (line 0 counts as near) and title+body Jaccard >= 0.25; one file and title Jaccard >= 0.4; or (RPP-B, `sameLineSameWords`) they share an **exact** file and line and, on stemmed words (a plural s, a trailing `ed` and the doubled consonant it leaves are cut; other endings such as `ing` are not), the titles or title+body share at least 2 words and at least 0.4 of the smaller word set (overlap coefficient, `SAME_LINE_SHARE`, `SAME_LINE_SHARED`). The last rule exists because two seats word one defect differently, so Jaccard stays low while the line and a few key words agree. The line must be exact on purpose: on the stored baseline, findings of different defects sit one or two lines apart with 0.36 overlap, and the related PR 6 pair (a wider Cancel pattern and the narrower Cancel-button finding, two lines apart) must stay two findings. The merged finding has the union of sites (at most 20, the rest counted in `omitted_sites`), the highest severity, the text of its most severe report (with equal severity, the first in input order), the seats that raised it, and `sources` (see Provenance). Thresholds are tuned on the stored baseline (two true pairs, a handful of near misses), so they are a small-sample fit: the margin is 0.47 and 0.5 against 0.25 at most for same-line non-pairs. Measured with `node scripts/review-eval/cli.ts merge` on the stored 2026-10-16 baseline of Triglav PRs 3, 6 and 8: before RPP-B it merged nothing (8 to 8, 8 to 8, 4 to 4, 2 of 2 judged duplicates left apart); now PR 8 is 8 to 6 (the late-Staff registration finding, P1, and the failure-writes-no-event finding, P2, each merged into one finding naming both seats), PR 6 and PR 3 are unchanged, and 0 of 2 judged duplicates are left apart. No catch or partial finding is lost (a test checks each is inside a merged finding of its seat). On the 2026-10-15 baseline outputs (private PRs) the old rules merged nothing wrongly; the new rule was not run on that data, which is not in the repository.

`blocks(finding)`: P0/P1 block unless triaged `invalid`; P2 blocks until triaged `debatable` or `invalid`; P3 never; a shadow finding never (see Shadow mode). A `valid` triage does not clear anything: a fix is a new head sha and a new review. `verdict` is `ok` or `changes`; any failed, timed-out or unparseable blocking seat makes the review `failed`, which never passes (a shadow seat's failure does not; no finished blocking seat does). Failed seats do not raise blockers; the guide says retry once, then raise one. `timeoutReviewRuns` (scheduler tick) fails a running seat 25 min after it started (`started_at`, so a late pick-up still gets the runner's 20 min) and a queued seat 25 min after the request; `expireStaleLaunches` drops unpicked launches after 10 min, one conditional update per launch. A failed review lists no blocking finding (its findings stay visible).

## The PR comment (`src/review-comment.ts`)

One comment per PR with the local review rounds, so a reader of the PR sees what the local gate did. The server builds the text; the Senior posts it. MCP tool `get_review_comment(job_id, head_sha)` (`getReviewComment`, READ, untrusted notice): a Senior with a live assignment on the job (held, lease not expired) or the job's Staff, refused unless `gateAt(job, head_sha)` passes. Returns `{job_id, head_sha, gate_review_id, marker, rounds, chars, body}`. The guide step is the last section of `src/guide/deliver.md` ("Triglav review comment"), pointed at from `senior.md` steps 6 and 8: `get_review_comment`, write the body to a file, find the Senior's comment by its marker (`gh api repos/<repo>/issues/<pr>/comments`, first line of the body), `gh pr comment <pr> --body-file` once, later `gh api -X PATCH repos/<repo>/issues/comments/<id> -F body=@<file>`. Never a second comment. The server cannot run `gh`, so this is a bar, not a boundary.

- `buildReviewComment` reads every `code_reviews` row of the job with status `done` or `failed` (running is skipped) in `created_at, seq` order and renders `reviewView` of each (`renderReviewComment`, pure, tested without a database). First line is the marker `<!-- triglav-local-review job=<job_id> -->`. Per round: shas (12 chars), verdict or failure reason, seats (runtime, model, effort, the lens in a code span and a fixed `shadow` mark, secs, tokens in/cached/out, cost or `n/a`), merged findings (a fixed `Shadow, never blocks:` prefix on shadow ones, severity, title, up to 5 sites, seat count, triage and reason). The severity counts leave shadow findings out and add `shadow N`. No finding body, no link, no dashboard address.
- Untrusted text goes through `codeSpan`: control, format and line-separator characters and newlines collapse to a space, text is cut at 300 characters, and the fence is one backtick longer than the longest backtick run in the text (a space pads a text that starts or ends with a backtick). Only fixed text, numbers and shas are outside a span. `assertNoSecrets` runs on the whole body; a hit refuses the comment.
- Size: `MAX_COMMENT_CHARS` = 60000 (GitHub allows 65536). When over, older rounds shrink to one line (counts per severity), then the newest round's findings are cut (100, 50, 20, 10, 5, 0), then the oldest lines are dropped with a count.
- Tests: `test/review-comment.test.ts` (code span, hostile text per field, marker, cap, card commands, tool auth, gate refusal, secret refusal).
- Known limit, not part of this change: `reviewView` and `finalizeIfDone` sort rows that hold large JSON, and MySQL's sort buffer failed with "Out of sort memory" in `finalizeIfDone` in a test with 100 findings of 20 sites each (paths of about 130 characters). Seen once, not investigated.

## Evaluation harness (`scripts/review-eval/`)

Dev only, by hand. Measures the panel against Copilot's findings on Triglav's own PRs; nothing in it runs in CI, in the Docker image (the Dockerfile copies `src` and `web`) or from a package script, and a test checks all three. Entry: `node scripts/review-eval/cli.ts list | score | merge | run` (README, "Evaluating the review panel").

- **Files.** `data.ts` (zod schemas and loaders for fixtures, stored runs and judgments, `checkJudgments`), `score.ts` (pure scorer and table), `merge.ts` (production `mergeFindings` over a stored run, and `duplicatesAfterMerge`, which counts the judged duplicates the clustering still keeps in two clusters, by seat and index), `run.ts` (the live path), `lean-prompt.ts` (the lean prompt, below), `cli.ts` (`refuseInCi`, `pickSeats` (the default panel's seat names, the lens seats included, plus `strong-2` to `strong-4` for an arm that repeats the strong seat; `seatPrompt` passes a lens seat's lens to the prompt, and `SEAT_ESTIMATE.lens` is a guess made before any lens run; `checkPromptSeats` refuses `--prompt lean` for a lens seat, since the lean prompt has no lens section; a stored lens seat keeps `lens` and `shadow` (optional in `SeatRun`), and `merge.ts` reads that flag, else the default panel's flag for the seat name (runs stored before it), so the harness clusters as production does), `pickPrompt`, commands).
- **Lean prompt (plan PR C, Q5).** `scripts/review-eval/lean-prompt.ts`: `leanReviewPrompt` and `variantPrompt(variant, input)` with variants `production` (exactly `buildReviewPrompt`) and `lean`. Harness only: no file under `src/` or the runner imports it (a test checks), so production sends what it always did. `run --prompt production|lean` picks it per arm (default production; `pickPrompt` refuses a misspelt name before any tokens are spent), `seatPrompt(fixture, seat, diff, prompt)` and `SeatDeps.prompt` / `FixtureDeps.prompt` carry it, and the stored run has an optional `prompt` field (runs stored before it, such as the baseline, have none and used production). `checkResumedPrompt` (cli.ts, before anything starts) refuses to finish an arm whose stored fixtures used another prompt. The lean text keeps the questions, repository rules, claims and verify-and-group steps, folds the edge cases and tests into the questions, and replaces "Search, always" with "search only what the diff cannot answer", stopping after about 15 commands (`LEAN_COMMAND_BUDGET`). Its task section is cut out of the production prompt at the `## The task` heading, so the data markers, the notes and the previous-round list are production's own text and cannot drift. No lean run has been done, so there is no measurement of it yet (the plan's arm A5): production switches only after numbers favour it, in a separate small PR.
- **Manifest, modes, budget (2026-10-17).** `runFixture` stores a run `manifest` (mode, repeat, harness rev and dirty flag, diff SHA-256, requester runtime, Codex window value, dropped seats, times) and a seat `manifest` per seat (CLI version from `detectRuntimes`, requested and effective config, fallback reason, prompt SHA-256, repeat, shuffle seed when `REPEAT_MEMBER` matches, rejected and zero-site counts, failure, every attempt with its usage and `charged` tokens). `--mode fixed` runs seats as named (`fixedSeats`); `--mode production` calls `resolveSeats` through `productionSeats` / `armSeats` (cli.ts) with what `detectRuntimes` found, `--requester` and `--codex-used`. A seat whose effective config differs from the requested one (`substituted` in data.ts) is left out of the arm's rows and scored under `substitutedLabel` (`<seat> as <runtime> <model> <effort>`); a fixture with no seat left is listed in `ArmScore.unscored` and adds nothing to the arm. A fixture's wall time is its manifest's elapsed time when it has one. `runArm` admits a fixture only when the sum of `estimateSeatTokens` fits the `Budget` (an admission stop: running seats are never cut; exit code 2 and the not-started list on a stop); `chargedTokens` charges reported usage, the estimate when a process ran without usage, 0 when none started. A killed or cut process loses its answer (`reviewerReport` empties it), but `attemptSeat` still reads the usage from the process's own output (for a run over the cap, `runReviewer` keeps what fit in `cutStdout`, which `reviewerReport` never sends; such an attempt is marked `cut` and charged at least its estimate, since usage after the cut was not read, and the scorer counts `attemptsCut`); a retry whose command cannot be prepared ends the seat as an unstarted attempt and keeps the earlier attempts; the attempt records `started`, and the scorer counts `attemptsWithoutUsage`. `--retries` reruns a failed attempt only when its estimate fits, and every attempt's usage is summed. `limiter` bounds processes (`--concurrency`). `checkResumedPrompt` also refuses another mode or repeat. Options are checked in `runOptions`. Without `--fixtures`, `run` covers the dev split only (`pickFixtures`); held-out fixtures run only when named. Docs: `scripts/review-eval/README.md` and `DECISIONS.md` (scope, split, deferred decisions).
- **Live path.** `run.ts` builds nothing of its own: `worktreeDiff`, `buildReviewPrompt` (or the lean one) + `reviewPrompt`, `claudeReviewArgs` / `codexReviewArgs`, `runReviewer`, `reviewerReport`, `parseReviewerOutput` and `staffStartEnv`, so a seat has the runner's access and no Triglav secret. `REVIEW_STDOUT_MAX` and `REVIEW_TIMEOUT_MS` are copies of the constants in `scripts/runner.ts` (a test compares them). `run` needs `--yes`, refuses when `CI` is set, writes raw output under `review-eval-out/` (git-ignored) and keeps a finished fixture of an arm, so a rerun never pays twice. It does not check the Codex or Claude plan limits. A failed seat is stored with `error` and no findings, and the scorer counts it as failed.
- **Data** (`test/fixtures/review-eval/`). `prs/<id>.json`: PR, full base and head sha (the head of Copilot's first review), title and the PR description cut before anything written after the review, and per Copilot finding `id` (`<fixture>-r<round>-<letter>`), round, severity (Copilot's own `high`, `medium`, `low`, never mixed with P0-P3), file, line and a label in our own words. Never copy Copilot's text, and nothing from a private repository (a test greps for it). A finding of round 2 or later carries `ceiling` (true when the code was already wrong at the round 1 head) and `ceiling_basis`. `runs/<arm>/<id>.json`: the stored seat output. `judgments/<arm>.json`: per panel finding `seat#index`, its title (checked against the run), and `catch` (same cause and fix, names the Copilot id), `partial`, `valid`, `invalid` or `unsure`, plus `dup_of` for a repeat of another finding. A finding with no judgment counts as unjudged. Optional on a judgment: `validity` (valid, invalid, unsure; must agree with valid, invalid and unsure), `severity` (P0-P3) and `evidence` (reviewed sha, which must be the run head, site, trigger, expected, actual, reasoning, `reviewers` single or two). Optional `misses` per fixture give a cause (`MISS_CAUSES`) for an uncaught Copilot finding. A fixture has a `split` (dev or held-out) and may have no Copilot finding (with `findings_basis`).
- **Scoring** (plan section 7.4, `docs/plans/review-panel-parity.md` while it exists). Per fixture, in total and per seat: R1 recall, ceiling recall, valid extras, noise (`invalid` only), unjudged (`unsure` or missing, always printed beside noise, which is a floor), dup, partial, finding count, input tokens with the cached ones apart (Codex's `tokensIn` already holds its cached tokens, Claude's does not, so `seatInput` adds them), output tokens, wall seconds (slowest seat) and seat seconds, and Claude's cost (Codex reports none, so `n/a`). Precision is valid over valid plus invalid among unique findings (`validityOf`), with a pessimistic and an optimistic bound that count findings without a validity judgment as invalid and then as valid. Incomplete seats (`incompleteReason`: failed, rejected findings, zero-site findings) are listed in their own section and stay in the totals.
- **Baseline.** `runs/baseline` and `judgments/baseline.json`: the default panel on PRs 3, 6 and 8, one run per seat, scored by one reader who knew the seat. It scores 7 of 12 round 1 findings (strong 7, cheap-claude 3), ceiling 10 of 17, 20 findings, 6 valid extras, 0 noise, 0 unjudged, 2 duplicates (the PR 8 pairs) and 1 partial; precision 18 of 18. tg6 strong#0, #4, #5 and the validity of tg3 strong#1 were judged on 2026-10-17 by one reader, with evidence. Set T also has PRs 1, 5, 7, 11 and 19 without stored runs (1, 7 and 19 held out; 1 and 5 round 1 only). The PR 8 seats were given a description that already listed the fixes to Copilot's round 1 findings; the fixture now cuts it, so a new run of PR 8 is not comparable with the baseline. PR 6's description reached the seats cut at 4000 characters, before its Copilot section. One run per cell: a difference of one or two findings is not a result.
- **Lens run (2026-10-20).** `runs/lens-haiku` and `judgments/lens-haiku.json`: the two lens seats alone (Haiku 5.5 medium, fixed mode, production prompt with the lens section) on the dev split (PRs 3, 5, 6, 8, 11), one run per seat, judged by one reader not blind to the seat. 6 of 17 round 1 findings caught (contracts 3, integrity 4, one shared), 4 valid extras, 4 invalid, 0 unsure, 3 judged duplicates (all merged by `mergeFindings`), 3.68M input tokens (3.01M cached) and 0.11M output, $0.24, about 5 minutes. None of the baseline's misses (tg8-r1-d contract, tg6-r1-b limit, tg3-r1-a, tg3-r1-b, tg6-r1-d) was caught. One run per cell: a sanity check, not a result.
