# Initiatives

New initiative from New job (`src/initiative-create.ts`, `POST /api/initiatives/new`) checked on 2026-11-20. Verified against the code on 2026-11-19 (phases 1 to 5 of docs/plans/initiative-room.md: the design and the Architect, job cards and gates, Staff routing to the Architect, and phase 4: changed since start, addenda, the merged-PR read, the met-gate reconcile, the deployed check and the gate mark log). If you find this out of date, fix it in the same PR. The invariants are in AGENTS.md ("An Architect reads one initiative and proposes; the Client decides", "An Architect answers Staff only with a verified citation", "The runner runs fixed gh commands for the initiative gates", "Phase 4 adds two more fixed, read-only gh paths"); this is the map. Phase 5 (references) is built, including research linked to an initiative and the file overlap warning on Start. See "References and the room (phase 5)" below.

## Flow

Two ways start an initiative. **New job**, choice New initiative: the Client gives a title, 1 to 10 repositories and a prompt, and `createInitiative` makes the key, the repository slugs and version 1 (trigger `create`, `trigger_ref` NULL, summary "Created from the New job form"), then the same insert and Architect chat as an import. The body is strict: a `key`, `doc`, `research_job_id` or any other field is refused by name. Without `ORCH_HOST_HOME` there is no home bound (`checkRepoPath` still refuses `~`). The page opens `#/initiatives/<key>`. **Import** (below) keeps a design file.

1. The Client imports a JSON file (`ImportSchema`: key, title, repos, cap, milestones_started, version, source, doc). The design is checked whole; the first version is the given `version` (default 1), trigger `import`, `trigger_ref` = source. An Architect chat (kind `architect`, state stopped, `insertArchitectChat` in `src/chat.ts`) is created with it. A second import of the same key is a conflict (`tx()` holds the global write lock, so imports run one at a time).
2. A Client message in the room's pane is a normal chat `send` command. `nextCommand` adds `chat_kind: 'architect'` and `architect` (key, title, repos, model and effort from the `architect` role, Claude Code only).
3. The runner prepares the worktrees (below), mints the chat token, writes the 0600 MCP config, and starts `claude` with `architectArgs` in the initiative folder. A repository it could not prepare becomes a system message in the chat and a line in the prompt.
4. `propose_design_revision` checks the ops against the current version and the initiative's repositories (`checkRepos`, as at import), then stores the revision (pending) and its `apply_design_revision` card in one transaction (`placeAction`; `announceAction` after the commit). A refused card (`MAX_PENDING`) stores no revision. The card text is `describeStoredRevision`: built from the base version and the stored ops, never from the model's words, capped by `cardText` (the room's History has every change).
5. Confirm: `applyRevision` locks the initiative, refuses (and marks stale) a revision whose base is no longer current, and inserts version N+1 with trigger `chat`, `trigger_ref` = the revision id and the changed ids. Deny or expiry: `closeRevision`, in the same transaction that moves the card (`Def.close` gets the connection). The open room drops the waiting revision when its chat stream shows the card's new state; no event row is written. A removed block is stored among the version's `changed` ids (History names it; `updated_in` skips it). A second click does nothing (the action moves state in one locked step). On an archived initiative `applyRevision` throws `is archived` before it changes anything; `decideAction` then marks the card failed, and the revision stays pending until the scheduler's `expireStaleCards` expires it as an orphan after the action TTL.

## Cards, Start and gates (phase 2)

1. The Jobs tab reads `GET /api/initiatives/:key/jobs`: every card of the current version, its state from `evaluateCards`, its gates and the running count. Nothing else decides a state.
2. Start: `GET .../start` shows what would be sent (`previewStart`). `POST .../start` with `started_from_version` (`startCard`) takes the initiative row lock, plans again, and refuses when the design version differs from the one previewed, when the card is not Ready, or when its repository is not in the settings. Then `queueRequest` queues an `implement` request on the card's repository and base, and an `initiative_card_starts` row records the version it read. Over the cap, Start still starts and the response carries the warning.
3. Merged gate: `queueGateChecks` (scheduler tick) queues a `gate_check` launch for an open merged gate whose source job has a delivery with a PR in the card's repository (the source is the job of the card the gate names, from its latest start, following a retry through `job_requests.retry_of` (`latestStarts`), and the delivery of that job or of its subjobs). A job with several delivered PRs (subjobs) queues no check: one `gh` call checks one PR, and the Client marks that gate by hand. A job with a subjob that is not done or cancelled is refused too: the check waits until every subjob is done or cancelled. The launch carries the gate row id as `run_id`. At most one check per gate every `GATE_CHECK_MS` (10 min), and none while one is pending. The due gates are taken least recently checked first, and a gate never checked goes first of all, so a slow gate cannot starve the rest. Only one `gate_check` is queued or running at a time across all initiatives (`queueGateChecks` returns early while one is unfinished). `gateCheckLaunch` re-reads the source when the runner picks the launch and passes only the PR number and the slug. When the source is refused (no job, no delivery with a PR, several PRs, a subjob not yet done or cancelled), nothing is queued and no check runs: the reason is stored as the gate's evidence under `not_checked`, without `checked_at`, so the first real check is not delayed, and the Jobs tab shows it as "Not checked" while the gate is open. A refusal that the runner finds when it picks a queued check is stored the same way and clears `checked_at`, which the queue had set. A Start of the card a gate names clears the `met_by` check marks of the gates that wait for it, so each waits for the new job; a mark the Client made stays. Reopening a done job (`reopenForDelivery`) does the same for the cards whose latest start is that job (`clearCheckMarksForJob`; for a subjob, the root job's start), and `mergedSource` then refuses the card with `not_checked` until the reopened job itself reports a delivery after the reopen. A job reopened and then cancelled cannot deliver, so its reopen is answered by a delivery of a live job of the card after the reopen instead. A Start and a reopen also clear the checked time, evidence and refusal of an open dependent gate, not only its check marks.
4. `recordGateOutput` (the runner's `gate-output` call) marks the gate met only when the JSON says MERGED with a merge time and a merge commit, the PR is the source's (its number and slug come from the latest delivery's `pr_url`; the head of the PR is not compared). Any other answer is stored as `evidence` (the state, or `error`), with no mark. A source refused after the check ran (a reopen, or a second PR delivered meanwhile) is stored as `not_checked` without `checked_at`, so it gets no cooldown, and also gets no mark. The launch stores the PR it picked in `launches.source_pr` (`slug#number`, migration 057). An answer whose source is another PR by the time it is recorded (a replacement start, for example) is discarded with no evidence and no `checked_at`, so the current source is checked at the next pass. A launch with no stored source (made before migration 057) cannot tell a moved source from a wrong answer, so an answer that names another PR is discarded with no evidence and no `checked_at`, as a stored source is; an answer that names the current source is compared as before. An archived initiative stores nothing: `recordGateOutput` returns `recorded: false` before it writes evidence or a version. A gate that a revision removed from the design since the check was queued gets no answer either (`mergedGateInDesign`; `gateCheckLaunch` cancels the launch the same way). A met gate writes version N+1 with trigger `event` and `created_by` scheduler: only the T-status line changes, with one line at the top. The PR, the merge time and the merge commit stay in the gate's evidence (the Start prompt reads them there). No line is ever cut. A line that would take the T-status block past `MAX_BODY` (20000 characters) is not written; the version is still written, and the gate's evidence gets `status_line_skipped`.
5. Manual mark: `markGate` takes a reason (required, at most 500 characters, `assertNoSecrets`). Decision and milestone gates are refused, and so is an archived initiative (as for Start). The mark writes version N+1 with trigger `client_edit`, and its T-status line carries the reason. A client_step mark stores its checkpoint's hash, and a mark that is open again (its checkpoint changed) can be marked again.
6. Start a milestone: `startMilestone` refuses an archived initiative, a name that no card gate waits for and a milestone already started. It adds the name to `initiatives.milestones_started`, which lists the started milestones, and writes version N+1 with trigger `client_edit`.
7. A retry (`retryJobRequest`) sets `retry_of` on the new request, so the card's latest start follows it. A dismissed request that never reached a job holds no card and no cap slot (`activeStart`, `runningCardJobs`), and a retried request is replaced by its child, so a chain holds one slot. `retryJobRequest` runs in one transaction, refuses a second retry of the same request, and refuses a retry of a start that a newer start of the same card has replaced (`assertNotSuperseded`), refuses a retry when the initiative is not active (for every card, running or not), and, unless the card is running, when the card is not Ready (`assertRetryStillReady`). `readJobRequest` and `lockRequestForRegistration` refuse a dismissed request.

## Staff routing (phase 3)

1. A wake: `emit()` calls `routeToArchitect` inside the same transaction. It wakes the initiative's Architect for a `refinement.staff_posted` event whose payload type is `discussion` (a Staff question on a job while it is refining; a progress post does not wake it) and for a `blocker.raised` event of kind `client_decision` raised by someone other than the Architect. Other events (a Senior's question, progress) do not wake it. The wake is a `send` chat command with the questions listed, prefixed `[Triglav] `; Staff's text is quoted and marked as data.
2. Batching: at most one wake per initiative in `ARCHITECT_WAKE_MS` (3 minutes). A question inside that window is kept in `initiatives.architect_wake_pending` (at most 20, the newest kept) and `flushArchitectWakes` (scheduler tick) sends it once the window has passed. Nothing is pushed to the open room; the Architect reads the wake from its chat.
3. Answer from a decision: `answer_staff_question` with `{decision: "D<n>"}` (the decision must exist in the current version) posts at once as the Architect, with `Answered from D<n>, design v<n>.` in the body. A blocker answer (`blocker_id`) also resolves the client_decision blocker in the same transaction (`resolveDelegatedTx`), marked delegated.
4. Answer from code: `{code: {repo, path, line, sha, quote}}` inserts an `architect_answers` row in state `checking` and a `quote_check` launch (`run_id` = the answer id, `runtime` git). The runner takes the launch and runs `git -C <repo> show <sha>:<path>` (argv, no shell, `staffStartEnv`, 60 s timeout, 2 MB buffer, output capped at 600000 characters) and posts the output to `/api/runner/:id/quote-output`. `recordQuoteOutput` posts only when the quote is on the cited line (spaces squashed on both sides); otherwise the row is `refused`. A quote shorter than 8 characters after whitespace is collapsed is refused by the citation schema. A launch that never runs, is lost, or finishes without its output refuses its answer (`failQuoteCheck`, also called by `finishLaunch`). A refused answer is never posted.
5. Uncited: the tool schema refuses an answer without a citation. A citation that is neither form is refused by the schema.
6. Escalation: `escalate` (a question, a recommendation, why the Client decides, what was checked) raises a client_decision blocker with the Architect as raiser and writes an `escalated` row. The same open question reuses its blocker. With `blocker_id` (Staff's open client decision of the job) it writes the `escalated` row on that blocker and raises nothing. The question is taken from the blocker row, not from the input: the id, the job, the kind and the open state are checked, and nothing matches text.
7. Accept: `acceptEscalation` posts the recommendation as the Client on the general thread and resolves the blocker, in one transaction, with the row locked. A blocker that is no longer open refuses the whole Accept and posts nothing. The row becomes `posted` with its target `blocker`, so it stays in the Inbox as a Reopen item. A plain Client resolve of the escalation's blocker (the Decisions page, a typed answer, an Operator decision) differs in `resolveBlocker`: it posts the resolution as the Client, sets the row to `posted` with the resolution as its answer and target `thread` in the same transaction, so the row leaves the Inbox and cannot be reopened. Whether the Decisions-page Accept should behave like the room's Accept is the Client's decision.
8. Reopen: `reopenAnswer` takes back a posted answer to a client decision (a delegated answer; a thread answer cannot be reopened), in one transaction with the row locked: it raises a new client_decision blocker with the answer as its recommendation, marks the old row `reopened`, and adds a new `escalated` row for the new blocker, so the Inbox lists it until the Client accepts it or answers in the room. It is refused once Staff has posted on the thread after the answer. The Architect cannot answer its own escalation (`answerStaffQuestion` refuses a blocker it raised).
9. Inbox: `openAnswers` lists escalations and delegated posts (target `blocker`) across initiatives; the room's Inbox tab lists its own. The answer text is shown as plain text.

## Merged work, deployed gates, addenda (phase 4)

1. A merged gate that becomes met (`recordGateOutput`) calls `queueMergedPrRead`: once per initiative and PR, a `pr_read` launch (runtime gh, `run_id` = the `initiative_pr_reads` row, no agent, empty cwd). The runner runs `prBodyArgs` and posts to `/api/runner/:id/pr-output`. `recordPrOutput` checks the JSON against its schema (the number and slug are not compared with the answer: the argv names the pull request), and wakes the Architect with a `merged_pr` ref. A read that cannot finish (the launch expires or is lost, or gh fails) is stored with its reason (`failPrRead`).
2. A deployed gate (`check: 'deployed'`): `deploySource` takes the repository, workflow, job, step and base from the initiative settings, and the merge commit and time from the source's met merged gate. The launch's `source_pr` is `slug@merge` (`deploySourceKey`), so a changed merge discards the answer. The runner's calls are listed under Runner check. `recordDeployedOutput` lets `provesDeployed` decide: `decidingRun` takes the newest push or workflow_dispatch run in which the named job has completed (a run whose job still waits is skipped; a newer failure wins over an older success). A refusal is stored as `not_proven` with the reason, without a mark. A mark writes the gate row only (`met_at`, `met_by` `check`, `checked_at`, `evidence`): no design version and no status line. It also writes one `initiative_gate_marks` row (item 6).
3. Changed since start: `changesSinceStart` compares the card's fields at the version its start was made from with the current version (`changeOfStart` does the same for one start, which an addendum uses). The card shows the change until a confirmed addendum for that job (`applyAddendum` calls `acknowledgeCard`) or a Client dismiss with a reason (`dismissCardChange`, logged in the card's acknowledgement columns).
4. Addenda: the Architect's `propose_addendum` stores a pending addendum with the card's change. The Client confirms it on the card; `applyAddendum` posts the text on the job's General thread as the Architect, with the design version. A post the board refuses (six in a row) throws `RetryableAction`, and `decideAction` leaves the action pending with the error.
5. A design change that alters the text of a met gate reopens the gate when the revision is applied, unless `keepGateMet` has logged a keep for that revision and gate (both texts kept in `initiative_gate_keeps`).
6. Gate mark log (migration 063, `initiative_gate_marks`; `logGateMark` and `logClearedMarks` in `src/initiatives.ts`): one append-only row for each change of a met state, in the same transaction. `set` comes from a merged or deployed check (`met_by` check) and from a Client mark by hand (`met_by` client). `cleared` comes from a replacement start and a reopen (the removed mark is in `evidence`) and from a revision that changes or removes a met gate (both texts). `keep_met` is written when the revision applies (the keep takes effect then) and holds both texts and the reason. A client_step mark whose checkpoint steps change reads as open without a write, so its `cleared` row (reason: the steps changed) is written when the gate is marked again. Never update or delete a row. The room reads only the `keep_met` rows (History, `getInitiative`). `get_initiative` reads the gate rows (`met`, `met_by`, `met_at`), not the log.

## References and the room (phase 5)

1. Quote chips (`src/architect-refs.ts`): the Architect's composer sends `{text, refs}` to the chat message route (`architectText` in `src/server.ts`, at most 10 refs). Each ref names a block, a design version, a text field of the block and optionally the selected text (at most 4000 characters). `architectMessage` reads every chip from the stored version of the chat's initiative (`versionOf`, then `quoteOf`); the browser's copy only helps find the place. A chip with a missing block, version or text is refused and nothing is sent. The message holds each quote as `> ` lines under `Reference N: block.field, design vN.` and says the quoted lines are data. A message without refs goes to `sendChatMessage` unchanged. Chips live in the page state, so a reload clears them.
2. Quote buttons (`web/src/initiatives.tsx`): `QUOTE_FIELD` says which text field each block kind quotes (text, decision, open, contract: `body`; card: `goal`; wave: `when`). `SelectionQuote` shows "Quote selection" over a selection inside a `[data-block][data-field]` element. Both add a chip above the composer.
3. Download as markdown: `GET /api/initiatives/:key/versions/:version/markdown` (a Client session route, not in `OPEN_API_ROUTES`) returns `designMarkdown` (`src/design.ts`) as an attachment: every block of that version, in order. `versionMarkdown` (`src/initiatives.ts`) makes the filename.
4. Gate states for the Architect: `cardStatesOf` gives each gate `met`, `met_by`, `met_at` and `reopened` (from the gate rows, no evidence). `get_initiative` returns them in `cards`. History lists every `keep_met` row, newest first (`getInitiative` returns all of them as `keeps`). `get_initiative` takes an optional `cards` list of card keys, so a large initiative is read in parts under the reply cap.
5. Your-step cards: `cardsView` gives each card `steps`, the steps of the checkpoint each unmet `client_step` gate names. The Jobs tab shows the gate as "Your step: label" with the steps as a numbered list. The first code span of a step is its prepared command: a Copy button copies it (`CopyCommand`, `navigator.clipboard.writeText`). A span of more than 300 characters, or one with a line break, gets no button (the limit is in `commandOf`; `StepList` uses `stepParts`). Copy only copies text in the browser; no route runs a command.
6. Checked facts: a delegated answer in the Inbox shows its citation (`Cited`). A code citation reads "Checked: path:line at sha12 (repo), verified <age>", where the age is the time since the answer's `decided_at` (when the Architect's check was recorded), not the commit date. A decision citation reads "Cited: design decision Dn". Escalations show their own why-client text instead. An answer posted to a thread is shown only on that thread.
7. Card PR and merge date (criterion 8, decided by Staff in message 5562): the card whose own job merged shows "Merged (checked)" with the PR and merge day from the evidence of the merged gate that names it (`mergedSourcesOf`, keyed by the source card, one line per PR and time, `source-merged` test id). The card that waits for the merge keeps its one "Merged gate <card> (checked)" line per gate (`mergedGatesOf`, keyed by the waiting card). `mergedChecksOf` lists each checked gate with its source. The card's own PR slot shows only the design's `pr`.
8. The pure rules are in `web/src/initiative-view.ts`: `commandOf` (the step's command), `stepParts` (its text and command), `quotableIn` (whether a selection can be quoted), `citedLine` (the Checked line), `ageText`, `mergedChecksOf`, `mergedGatesOf`, `mergedSourcesOf`, `MAX_QUOTE`, `quotableWhole` (whether a whole field can be quoted) and `popoverAt` (where the Quote selection popover goes). They are tested in `test/initiative-view.test.ts`.
9. Phone width: the room's grid items have `min-width: 0` (`web/src/styles.css`), so at 375 px the page does not scroll sideways. The e2e spec for this is `e2e/initiative-phase5.spec.ts`.

## Research and the overlap warning (phase 5 follow-up)

Built for PRM-567CB7 (criteria 1 to 9 of that job; the Client's decisions are blk_bf98404db3c41bed and dec_a27ea261466e1612).

1. Research link (`src/initiative-reports.ts`, migration `064_initiative_reports.sql`, table `initiative_reports`: one row per linked job, with the initiative and `linked_at`). `linkReport` refuses a job that is not `kind = research`, a job on a repository the initiative does not name, a job linked to another initiative, and a second link. `unlinkReport` refuses a job that is not linked. `reportsOfInitiative` returns the linked jobs with their versions and the candidates (research jobs on the initiative's repositories that are not linked). Routes, all Client-session only and not in `OPEN_API_ROUTES`: `GET /api/initiatives/:key/reports`, `POST /api/initiatives/:key/reports` (body `job_id`), `DELETE /api/initiatives/:key/reports/:job`. The room's Research tab (`ResearchTab`, `tab-research`) lists and links from these. The DELETE is sent with `{}` as its body: the web `post` helper sends a JSON content type, and Fastify refuses an empty JSON body.
2. The Architect reads a report with `read_report(job_id, version, offset)` (`readReportSlice`). A slice holds at most `REPORT_SLICE_CHARS` (30000) characters, is wrapped in `<report_text>` tags as data, and gives `next_offset` (null at the end). One refusal text covers another initiative's report, an unlinked job, a job that is not research and a missing version: "No linked research report has that version." `get_initiative` lists the linked reports (job, versions, summaries), never their bodies.
3. Citations and sources. `answer_staff_question` takes `{report: {job_id, version, quote}}`; `assertReportQuote` checks the link, the version and that the quote (at least `REPORT_QUOTE_MIN`, 8 characters) is in the stored body. The answer then reads "Answered from research report <job> v<n>.". `propose_design_revision` takes optional `sources` (at most 5, each `{job_id, version}`), checked by `checkedReportSources` inside the transaction and stored in `initiative_revisions.sources` (migration `066_revision_sources.sql`). `describeStoredRevision` writes each source on the Confirm card from the database, as "Research source (unverified): <job title>, report version <n>.".
4. Overlap warning (`src/card-overlap.ts`). The runner adds `changed_paths` (`{paths, more}`) to the reviewer output it already posts (`reviewerReport` in `scripts/code-review-run.ts`). The list is the changed paths `changedPathsOf` builds from the repository rules diff: at most `MAX_CHANGED_PATHS` (300), the rest counted in `more`, and a path with a backslash or a bidi control is left out. `recordReviewOutput` checks the list with `parseChangedPaths`, all or nothing, and stores it in `code_review_run_deltas.changed_paths` (migration `065_review_changed_paths.sql`). A bad list is dropped and never fails the run. There is no new launch kind and no new git command.
5. Matching. `overlapOf` reads each running implement job that was started from a card of the same initiative and runs in the card's repository (`liveCardJobs` in `src/initiative-jobs.ts`). For each job it reads the newest finished review run that stored a list; the live subjobs of a split card in the same repository are read the same way and merged under the root. It reports the listed paths that touch the card's likely paths. `likelyPaths` reads path-like tokens from the card's `scope`, `accept`, `verify`, `traps` and `safety` fields (not `out`, not `goal`), at most 4000 characters per field. A token matches as an equal path or as a folder prefix (`touches`). Generated lockfiles are left out (`generatedPath`). The card has no new field. `previewStart` returns `overlap` next to the prompt and never changes `can_start`. The Start confirm (`OverlapNote`) lists the paths as text, with the job and the reviewed heads (for a split card, one per distinct head of the root and its live subjobs with a review list), and says when the source is not origin, the list was cut, a running job has no list yet, or the card names no path.
6. Staleness. The data is as old as the oldest of the lists it merges: for a job, the newest finished review run that stored a list; for a split card, the newest such run of the root and of each live subjob (`reviewedPaths` keeps the oldest time and the distinct heads). A running job with no such review has no data, and the preview says so. A started live subjob of a split card with no such review also makes the card no data (`unreviewed`). The root of a split card has no review of its own (a Senior cannot start on a job with subjobs, `src/jobs.ts`, and a review needs a held assignment), so a split card shows no data until one of its started subjobs has a finished review with a file list. A subjob counts as started when its status is in_progress, in_review or delivering, or when it is blocked from one of those (`previous_status`); a subjob blocked in planning or ready does not count. A subjob still in planning, ready or queued is not counted, and a subjob in another repository is left out of the merge. The warning still shows the parts that were read. A cut list (`more` above 0), or a list read at a base other than origin, that shows no overlap is marked incomplete.

## Worktrees

`~/.local/state/triglav/initiatives/<key>/<slug>` (folder 0700; `ORCH_INITIATIVES_DIR` overrides it for tests). Each is a linked, detached, locked worktree of the Client's checkout at `refs/remotes/origin/<base>`, after `git fetch origin <base>`. Every git call has `core.symlinks=false` (a link becomes a plain file holding its target), `core.hooksPath=/dev/null` and `GIT_TERMINAL_PROMPT=0`. The repository path must be inside the home folder and the top of a checkout; an existing folder is refreshed only when it is a worktree of the same repository. Refreshed only when an Architect process starts, not per message. `reapWorktree` refuses any path under the initiatives folder.
